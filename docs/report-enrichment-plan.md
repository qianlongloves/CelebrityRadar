# 深度报告内容增强路线图

> 面向二次开发者的规划文档：说明「还能从哪些维度丰富报告」、每个维度的**成本与门槛**、
> 以及为什么这样排序。落地进度见每节的状态标记，可直接对照代码阅读。

## 三条硬约束（决定了方案的排序）

1. **报告是全局共享缓存**：`report_cache` 一次生成、长期复用。**新增 Schema 字段对存量报告不可见** ——
   老报告的 JSON 里根本没有这个键。所以任何依赖新字段的维度都必须接受「存量报告看不到」，
   UI 必须能优雅降级（整卡不出，而不是显示空白或 0）。
2. **提示词在端上构造**（`src/utils/report.ts` 的 `SYSTEM_REALTIME`）：会员段落用
   `MEMBER_HINT_REALTIME` **只追加在会员的 system 末尾**，免费提示词逐字节不变 ——
   即「免费用户不该白付这部分的 token」。新增字段若进免费段落，等于给每次生成加成本。
3. **主包硬限 2MB**：不引图表库。现有做法一律是 CSS / View + transform 自绘
   （词云 = 标签墙，情绪条 = flex 比例条，折线 = 自绘几何）。

另有一条贯穿全项目的规矩：**只基于素材，不做推断**。算不出来或对不上出处的，宁可不呈现。

## 第一批：端上聚合（零上游成本，对存量报告立即生效）

与词云（M4-5）/ 热度趋势（M4-6）/ 数据 Tab（M2-4）同一条路线：不新增 Schema 字段、
不新增云函数、不消耗生成额度。**这也是唯一能立刻改善老报告体验的一批。**

| 维度 | 原本的空白 | 做法 | 状态 |
|---|---|---|---|
| 来源 × 情绪交叉 | 数据 Tab 有来源分布、也有情绪构成，但**没交叉** | 同一批 `dynamics` 换个切法：哪些来源在正面报道、哪些在质疑 | 已实现（`SourceTilt`） |
| 素材可信度画像 | `coverage` 只有 items / recent 两个标量 | 独立信源数、独立事件数、重复报道比、首报来源 | 已实现（`CredibilityProfile`） |
| 情绪走势 | `stance` 与时间线各摆各的 | **改为**「情绪 × 时间」分层柱 | 已实现（`SentimentTrend`） |
| 语录主题聚类 | `quotes` 是平铺列表 | 复用词云的 n-gram 口径，把语录归成 2~3 个主题 | 已实现（`extractQuoteThemes`） |

### 落地位置（第一批）

| 维度 | 聚合（`src/utils/`） | 卡片（`src/pages/`） |
|---|---|---|
| 来源 × 情绪 | `stats.ts` → `buildSourceTilt`（`SourceTilt`） | 主页数据 Tab：「来源 × 情绪」（`profile/index.tsx`） |
| 素材可信度 | `stats.ts` → `buildCredibility`（`CredibilityProfile`） | 主页数据 Tab：「素材可信度」 |
| 情绪走势 | `stats.ts` → `buildSentimentTrend`（`SentimentTrend`，桶骨架 `bucketize`） | 主页数据 Tab：「情绪走势」 |
| 语录主题 | `keywords.ts` → `extractQuoteThemes`（`QuoteTheme`） | 报告页：「语录主题」 |

两处复用关系（改一处必须一起想）：来源归并 `mergeSources` 被「报道来源分布」与「来源 × 情绪」
共用；分桶骨架 `bucketize` 被「时间分布」（含周报逐日分布）与「情绪走势」共用。

### 两处与初版设想不同的修正（记录原因，避免后人再绕回来）

- **「媒体立场分布」→「报道倾向（来源 × 情绪）」**。原名把 `sentiment` 说成了「媒体立场」，
  而 `dynamics[].sentiment` 标注的是**这一条报道的写法**，不是该媒体的编辑方针。
  按原名做出来会误导读者（「这家媒体偏负面」是个过强的结论），故收敛为「本报告收录条目的
  情绪归类按来源的交叉」，脚注写清口径。
- **「观点演化（stance × timeline）」→「情绪走势（情绪 × 时间）」**。`stance` 的字段是
  `topic / attitude / note`，**没有日期**，硬要对齐时间轴只能靠话题名与正文做字面匹配 ——
  那正是「推断」，与项目规矩冲突。改成对**带日期的动态**按情绪分层的月度走势：同样是「舆情
  随时间怎么变」，但每一个点都能在报告里逐条对上。

## 第二批：新增报告字段（同一次调用里多要几段）—— 已实现

成本增加有限（多输出几段 JSON），但**存量报告没有这些字段**，且免费段落一旦加长，
每次生成都多付 token。

| 维度 | 价值 | 注意 | 状态 |
|---|---|---|---|
| 结构化人物档案 | 现在只有 `intro` 一段散文，缺「一眼看清 who」的锚点 | 每条须带素材 url | 已实现（`profile`） |
| 关系图谱（合作者 / 对手 / 师承） | 「人-人」维度完全空白 | 关系必须出自素材，不得推理 | 已实现（`relations`，类别枚举四档） |
| 待观察问题（未来时间点 / 事件） | 把报告从「回顾」变成「可跟踪」 | 只写素材里已公布的时间点 | 已实现（`watchlist`） |
| 术语 / 背景注解 | 行话（如文娱「番位」）读者未必懂 | 定位为免费可见 | 已实现（`glossary`） |
| 近期争议与回应 | 现有 `memberNotes.risk` 是会员专属，但「近期争议」对免费用户同样是核心信息 | 建议从会员段拆出，或明确保留边界 | 已实现（`controversies`，取「明确保留边界」） |

### 落地位置（第二批）

| 维度 | 清洗（`src/utils/report.ts`） | 卡片（`src/pages/report/index.tsx`） |
|---|---|---|
| 人物档案 | `ProfileItemSchema` + `strictSourceOf` | 报告页：「人物档案」 |
| 关系图谱 | `RelationSchema`（`RelationKindEnum` 四档，`normRelation` 归一） | 报告页：「关系图谱」 |
| 后续关注 | `WatchItemSchema` | 报告页：「后续关注」（时间线之后） |
| 名词解释 | `GlossaryItemSchema`（**唯一不带 basis** 的模型段落） | 报告页：「名词解释」 |
| 近期争议与回应 | `ControversySchema` | 报告页：「近期争议与回应」（会员卡之前） |

### 落地时的三处口径（与初版设想不同的地方，记录原因）

- **事实字段没有「据公开资料」这个出口**。`analysisPoints` 是**判断**，指不出出处时退成
  「据公开资料」是一句诚实的兜底；而档案 / 关系 / 后续关注 / 争议是**关于本人的事实**，
  退成「据公开资料」会让一条凭空生成的事实看起来「有据可查」。故新增
  `strictSourceOf`：不在素材集合内的 url 直接返回空串，调用方**整条剔除**（`sourceNameOf`
  保持不变，只服务判断类字段）。
- **`glossary` 是唯一豁免出处的段落**。它解释的是行话的通行含义（常识），不是关于本人的事实
  断言 —— 素材里不会有「番位」的定义，硬要 basis 只会逼模型编一个出来。豁免的代价是它必须
  更短更少（5 条 × 50 字，比其余四段收得紧）。
- **`controversies` 与 `memberNotes.risk` 取「明确保留边界」而不是「拆出」**。两者读起来像同一
  件事，实际是两层：`controversies` 记**已发生**的争议与公开回应（事实，免费），`risk` 是
  **面向未来**的风险提示（判断，会员）。边界写进了 `MEMBER_HINT_REALTIME`：已发生的争议归
  `controversies`，风险段不复述。这样免费段与会员段各自成立，也不动既有的会员结构。
- **免费段落加长会顶过上游的默认输出上限**（本批落地后才暴露的坑，务必照做）。免费档此前不传
  `max_tokens`，用的是上游默认值（DeepSeek 4096）；本批往**免费**提示词里加了 5 段 JSON 之后，
  报告 JSON 长过了这个默认上限，尾部被截断 → JSON 解析不出 → 重试再失败 → 整份报告降级成纯文本
  简版：报告页的结构化卡片**成批消失**，看起来像功能被删了，还白付两次生成的钱。修法是让
  `aiProxy` 对**所有**请求下发输出上限（`llm.config.js` 的 `chatMaxTokens`，默认 8192），不再按
  会员分档 —— 输出上限是「这一轮要写多长」的客观需求，不是会员权益。第三批若还要往报告里加字段，
  先按这条把 JSON 长度估一遍；端上也会把上游 `finish_reason=length` 记进诊断日志，便于复核。

### 呈现层的遗留项（本批未做，见下）

第二批一次性加了 5 张卡，报告页确实更长了。此前提过的「折叠目录 + 锚点跳转」因此从
「可选优化」变成「下一个该做的东西」—— 但它只改组织方式、不加数据，与本批的字段改造
互不依赖，故单独留在这里。

## 第三批：需要新增检索或较大改造（建议单独立项）

- 同领域人物的**自动横向对照**（端上已有两人对比的底子，可自动挑 3 位同领域名人做一屏对照表）
- 关键转折点标注（需要更多素材与更细的时间对齐）
- 报告版本 diff：同一人物前后两次生成，标出「新增了什么」（`report_cache` 已有历史可依）
- 摘要长图 / PDF 导出（现有一句话卡可扩展）

## 呈现层（不加数据，只改组织）

报告加上这些卡后会很长。建议优先做**折叠目录 + 锚点跳转**，成本极低，
但直接决定「丰富」会不会变成「更没人看完」。
