## 二、P0 / P1 —— 前端可闭环，已执行

### O-1 「AI 提问」频道页每次进入最多 10 次云读 → 收敛到 3 次 ✅

**问题**（`src/pages/ask/index.tsx` 的 `load()`）：原实现是

1. `await readMemberState()` —— 1 次 `users` 云读；
2. `await listRecentHistory(PROBE_LIMIT)` —— 1 次 `history` 云读；
3. `Promise.all(rows.map(getCachedReport))` —— **`report_cache` 的 8 次独立云读**（`PROBE_LIMIT = 8`）。

三步串行 + 8 次单条往返，**每次 `useDidShow`（从任意 tab 切回本页）都会整体重跑**：
底栏页是最高频的切换目标，这里的「10 次往返」是白花的（`report_cache` 以 `personKey` 为主键，
本来一次 `in` 就能取回）。

**建议**：

- `readMemberState()` 与 `listRecentHistory()` 两者互不依赖，改并行；
- 在 `utils/cache.ts` 新增 `getCachedReports(keys)`：一次 `in('id', keys)` 批量读，
  **命中判定与 `getCachedReport` 完全一致**（`state === 'ready'` 且有 `report`），返回顺序与入参一一对应（缺位为 `null`）。

**收益**：切页往返 **10 → 3** 次；只读路径，无行为变化。
**风险**：低。`in` 由 `utils/db.ts` 的 `toCmd` 翻译为 `command.in`，已在同一适配层内。
**落地**：本次完成（`utils/cache.ts` + `pages/ask/index.tsx`）。

### O-2 「我的」页 AI 提问用量脚注与计费口径矛盾 ✅

**问题**（`src/pages/mine/index.tsx` 用量卡）：脚注写「本机统计（**发起即计，失败也算**）」，
但 `utils/qa.ts` 的实际实现是 —— `noteQaUsed()`（写 `qa:usage` 计数）**只在 `askReport` 成功后调用**；
被每日额度拦下、机审命中（`含不合规内容`）、模型报错这些失败分支**都不计数**，
`noteQaAttempt()` 只写 `qa:last_at`（维持 3 秒连点间隔），不碰计数。
即：**页面承诺「失败也算」，代码实际「成功才算」**。

**建议**：以代码口径为准改文案 —— 失败也扣额度对用户不公平，也与生成额度
「只有真拿到报告才 +1」（`utils/quota.ts`：refused / error / 缓存命中都不计数）的既有口径一致。

**收益**：账目类文案与行为一致；避免用户被多扣次数后认为「额度算错了」。
**落地**：本次完成（`pages/mine/index.tsx`）。`utils/qa.ts` 的注释本就写的是「成功才计入」，
不需要改；《开发计划.md》M4-8 与《联调手册.md》用例 23 的口径同步核对过，无需变动。

### O-3 「AI 提问」频道页空态不分「未登录 / 无报告」 ✅

**问题**（`src/pages/ask/index.tsx` 空态）：候选来自 `listRecentHistory`，而
`utils/history.ts` 在**未登录**时直接 `return []`。于是未登录用户看到的空态是
「还没有可以提问的名人 / 先去生成一份报告」—— 按这句去生成，会先撞上登录流程，
**指引与真实原因不符**。

**建议**：空态按 `useAuth().userId` 分流：
- 未登录 → 「登录后才能提问」+ 行动按钮去「我的」页登录（`switchTab('/pages/mine/index')`）；
- 已登录且无候选 → 保留原文案（引导去发现页生成报告）。

**收益**：首次进入底栏第二格的新用户不会被误导到一个必然失败的路径。
**落地**：本次完成（`pages/ask/index.tsx`）。

### O-4 频道页候选池只覆盖「最近查看过」的 ≤8 位 ✅

**问题**（`src/pages/ask/index.tsx`）：原候选 = `listRecentHistory(8)` 过滤出「缓存里有报告」的人。
两条漏口：① **关注了但没点进过报告页**的名人不在候选里（关注流里的报告是从 `report_cache`
共享读的，不写 `history`）；② `history` 上限 50 条（`HISTORY_LIMIT`）且写入时会裁剪，
生成过报告但很久没回访的人会被挤出候选。

**建议 / 落地**：候选改为「最近查看（8 位）∪ 我的关注」，按 `person_key` 去重后一次批量读探测，
探测名单总上限 20 位。**排序取「最近查看优先、关注补齐在后」**，而不是最初设想的「关注优先」——
选人条是横滑的，用户刚看过的人必须排在最前，否则「看完报告顺手追问」要滑到第 10 位往后找。
仍然**只读缓存**、绝不代替用户触发生成（本页最重要的边界，见 `pages/ask` 文件头）。

**收益**：关注流是从 `report_cache` 共享读、不写 `history`，所以「关注了但没点进过报告页」的人
此前**完全无法提问** —— 这是覆盖面的窟窿，不是排序偏好。
**代价**：多一次 `follows` 云读；与 O-1 叠加后切页仍是 4 次往返（会员态 / 最近查看 / 关注并行 + 1 次批量报告读）。
**遗留**：真机确认 20 位批量读的耗时（模拟器指标不可信）。

### O-10 会员「质」权益第一刀：模型分级 ✅

**问题**（`src/utils/member.ts` + `src/config/public.ts`）：会员权益表里**只有两个次数**
（生成 3→30、提问 5→30），没有任何「质」的差异。更能说明问题的是 ——
`public.ts` 的 `llm.models` 三档（含成本最高的 `deepseek-reasoner`）**对所有人开放**：
`pages/mine` 的「生成模型」卡可自由切换，`utils/llm.ts#resolveChatModel` 只校验「模型在不在清单里」，
云函数 `aiProxy` 更把端上传来的模型名**原样透传**给上游。
即：付费点只有「次数」，而最贵的那一档正在**免费送给所有人**。

**建议 / 落地**：

- **端上**：`public.ts` 每个模型加 `memberOnly`（极速版 `false`、标准版 / 深度推理 `true`）；
  `resolveChatModel(member: boolean)` 增会员参数 —— 非会员请求 `memberOnly` 档位一律回落默认模型
  （本机存量偏好同样被忽略，避免「切过再退会员」还能用强模型）；`pages/mine` 的模型卡对未解锁项
  显示「会员」小标、点击给开通引导（`showModal` → `pages/member`），不做静默失败。
- **云函数**（`cloudfunctions/aiProxy`）：新增 `MEMBER_ONLY_MODELS` 白名单 + `isActiveMember(openid)`
  （按 `_openid` 读 `users.membership.expires_at`，**读库失败按非会员**，与端上 `readMemberState` 同向）；
  `chat` 收到会员档位而调用者非会员时**静默降级**为默认模型并回传 `downgraded`（端上记进诊断日志 meta）；
  `search` 的 `count` 上限同口径分档（`FREE_SEARCH_MAX` = 20 **保持不变**，不得削减既有免费额度；
  `MEMBER_SEARCH_MAX` = 40 为 O-11 的深度模式预留）。
- **权益文案**：`MEMBER_BENEFIT_POINTS` 首条改为「标准版 / 深度推理模型」
  （`pages/member` 与 `pages/mine` 的权益简表同源展示，改一处两处都变）。

**收益**：付费点从「只有次数」变成「次数 + 模型档位」，同时**堵住一个正在漏钱的洞**。
**取舍**：端上判定保留 —— 但它只决定展示与请求值，真正的闸门在云函数（改包绕不过）；
两侧指向同一个模型，所以「设置页显示哪档 = 实际用哪档」对免费用户同样成立。
**代价**：`getChatModel` 每次多一次 `users` 读（取会员态）——与生成链路已有的 `peekGenerateQuota` 同级，
只在生成时发生，不在高频交互路径上。
**剩余人工一步**：**重部署 `aiProxy`** —— 守卫只在新版本里；未重部署时端上锁得住 UI、锁不住改包请求。
建议顺序「**先发端上、再部署云函数**」：反过来会让现网旧版本里切过强模型的用户立刻被降级
（这正是预期效果，但最好发生在「会员权益已对外」之后）。
**真机验证点**：① 免费号选标准版 → 弹开通引导且**不写入**偏好；
② 会员号切深度推理生成 → 耗时明显变长、诊断日志 `llm` 条目 `downgraded=false`；
③ 手工把 `model` 改成 `deepseek-reasoner` 直调 `aiProxy` → 返回 `model=deepseek-v4-flash` 且 `downgraded=true`。

### O-11 会员「质」权益第二步：深度模式与独家段落 ✅ 已落地（素材 / 输出 2026-10-07；信源分歧补于本轮）

**做了什么**（三件事都已接线，**`aiProxy` 需重部署后才生效**）：

1. **素材加厚只加在生成路径**：`utils/cache.ts#generateReport` 用 `peekGenerateQuota` **顺带回传**的会员态
   （`memberDeep`）决定是否加厚 —— 会员走 `utils/search.ts` 的 `DEEP_MAIN_COUNT = 24` / `DEEP_SOCIAL_COUNT = 16`
   （两条链路各自独立过云函数的 count 钳制，合计正好吃满 `MEMBER_SEARCH_MAX = 40`，不越界也留不出「要了却拿不到」的空档）；
   免费的 `fetchNews` 请求与改造前**逐字节一致**。⚠ 全文件**只有这一处**加厚：`refreshAllFeeds` / `refreshFeed`
   的两处 `fetchNews` 刻意不动 —— 那是每日 10 次的常态动作，放大等于常态成本翻倍而用户几乎无感。
   会员态取自**已有的**配额检查，不额外读库；配额检查失败时保持 `false`（放行的是免费口径，宁可少给不可误给）。
2. **输出上限按会员放开**：端上 `utils/llm.ts` 仅会员的请求体带 `deep: true`（免费逐字节不变）；
   `aiProxy#handleChat` 里 `deep = event.deep === true && (await isMember())`，只有它为真才加
   `max_tokens = MEMBER_CHAT_MAX_TOKENS(8192)`，免费版**不传 `max_tokens`**（用上游默认，不悄悄削免费用户一刀）。
   返回体带 `deep`，端上记进诊断 meta（出现「会员说切了深度推理但报告很快 / 被截断」时，一眼能看出服务端有没有真放行）。
   起因：报告正文是「多段摘要 + 逐条动态」的长 JSON，贴默认上限时尾部字段容易被截断，表现为「解析失败 → 重试 → 再失败」，
   代价反而是翻番的生成耗时。
3. **独家段落**：`utils/report.ts` 的 `MEMBER_HINT_REALTIME` 只在会员的 system 末尾追加（免费连这段 token 都不白付），
   产出 `memberNotes`（`compare` 对比视角 + `risk` 风险提示）与 `conflicts`（**信源分歧，本轮新增**，见 O-20 的会员侧）。
   报告页会员卡标题为「会员专享 · 深度解析」，`member && (report.memberNotes || report.conflicts)` 才渲染 ——
   **两个字段各自判空**（只带 `conflicts` 的报告不会因 `memberNotes` 缺失而整卡消失）。权益文案同步：`utils/member.ts`
   的深度模式 note 由「对比视角 / 风险提示」两段改为「**对比视角 / 风险提示 / 信源分歧**」三段。

**为什么当初押后、现在又能做**：原顾虑是成本与定价强相关。这一版把它拆开 —— 素材加厚与输出上限**只对会员**，
且加厚只发生在「一次生成、长期缓存」的报告路径上，成本可估；独家段落里 `memberNotes` / `conflicts` 都是
**零上游成本**（不新增任何检索 / 调用，只在同一次生成的输出里多要两段文字）。**仍未做**：O-18 的「对比问答」。

### O-20 报告质量：素材「事件归组 + 分级保留」+ AI 点评拆条 ✅（**全员受益**）

**问题**（免费用户的报告也有两处长期粗糙）：

- **素材选取是「顺序截断」**：`buildUserMessage` 按顺序装，装不下就**丢整条** ——
  预算紧张时模型看到的是「前面几条的全文 + 后面几条整条消失」，而不是「全部事件」。
- **点评是一整段**：`analysis` 是一坨 3~5 句综述，没有重点，也看不出每句判断的依据。

**做法**：

1. **事件归组 + 分级保留**（`utils/report.ts`）：标题归一化（`normalizeTitle`：只留中英文与数字）后取字符二元组，
   用 Dice 系数 ≥ `SAME_EVENT_RATIO(0.62)` 判同一事件（`groupByEvent`）。前 `FULL_ITEM_COUNT(10)` 个**事件**的
   代表报道给全文，其余（含同一事件的重复报道）压缩为 `BRIEF_ITEM_CHARS(160)` 的 brief，并在提示词里明确标「正文从略」——
   只够模型判断「这条在讲什么」，不足以据此展开叙述（这是刻意的）。仍超预算时只丢**已压缩**的尾部条目（`diagLog` 记 warn），
   **首条永远保留**。按事件计而非按条计：一件事被 5 家媒体报道，过去会一口气吃掉 5 个全文名额。
2. **点评拆条**：契约新增 `analysisPoints: [{ point, basis }]`，prompt 第 5 条改为要求拆条（每条 40 字内、要具体、禁套话）。
   `sanitizeReport` 里 `basis` 走 `sourceNameOf` —— 它只是素材 URL 的**引用位**，落库前按引号白名单换成**媒体名**，
   编造的 URL / 空值一律收敛为「据公开资料」（页面上不出现裸 URL）。上限 `ANALYSIS_POINT_CHARS(80)` / `ANALYSIS_POINT_MAX(4)`。
   **`analysis` 仍在契约里、仍落库**，由各条拼接（补句号）—— 它是问答上下文（`utils/qa.ts` 读的就是这个字符串）
   与降级简版路径（`SYSTEM_FALLBACK` 产出一整段）的共用出口，**拆条不牺牲下游**。
3. **报告页**：有 `analysisPoints` 就渲染列表（每条 = 判断 + 「依据：媒体名」），否则回落老缓存那样的整段 `analysis`。

**与 O-11 的边界**：这两项**不限会员**（免费用户同样受益），故单列为 O-20；会员专享的「信源分歧」（`conflicts`）
才算 O-11 独家段落的第三项（同一轮一起做的）。

### O-21 会员价值在报告页顶部可见 ✅

**问题**（O-10 / O-11 / O-20 把「质」权益做齐之后，价值的**可见性**仍是零）：

- 深度模式的权益此前只在两处出现：会员中心对比表里的一行字，以及**会员**在报告页滑到最底部才遇到的那张卡。
- 报告是全局共享缓存 —— 免费用户点开某位名人，读到的很可能**正是会员生成的那一份**，

- 反面做法（也是本次刻意不做的）：在报告正文里摆「灰掉的内容 + 开通会员解锁」。留白可以有，
  但不该以「把已有内容遮起来诱导付费」的方式出现 —— 全项目从 M4 起就守着「正文不设墙」这条线。

**做法**：在报告页横幅正下方（`pages/report/index.tsx`，首屏第二块）加一条**会员价值条**，
把「读它的人是不是会员」和「这份报告里**实际**有哪些专享段落」两件事分开讲，四态：

| 读的人 | 报告里有专享段落 | 文案 | 动作 |
| --- | --- | --- | --- |
| 免费 | 有 | 这份报告里已有 对比视角 / 风险提示…，开通会员即可查看 | 开通会员 › |
| 免费 | 无 | 会员生成时检索加厚，并多出 对比视角 / 风险提示 / 信源分歧 | 了解会员 › |
| 会员 | 有 | 本报告已含 对比视角 / 风险提示… | 查看 ›（页内滚动到那张卡） |
| 会员 | 无（老缓存） | 本报告为较早版本，未含…；下次生成时自动加入，不额外消耗额度 | 无动作 |

2. **会员态不做推销、不给生成压力**：老缓存没带专享段时，动作留空（`action: ''`），只如实说明。

3. **免费态的两个分支都必须说真话**：有内容时才说「开通即可查看」（这是可兑现的承诺，
   报告是共享缓存、开通后确实就看得见）；没内容时退回到「会员生成会多出什么」，**不承诺当前这一份**。
4. **样式**：会员态用极淡品牌底 + 品牌色标题（与「我的」页会员卡同一套视觉语言，表示「权益生效中」），

5. **`查看` 走页内滚动**（`Taro.pageScrollTo({ selector: '#report-notes' })`，对应卡片补了 `id`）：
   失败（低版本基础库不接受 selector）静默忽略 —— 滚动是增强，不是功能，不留任何用户可见的报错。

### O-23 收藏卡「补内容」：从一行信息到「看得出为什么值得存」 ✅

**问题**：O-16③ 给报告卡补了走势条之后，四类卡片的**内容**仍然只有一行 ——

- **报告卡**：一条热度刻度 + 一条走势。两者都在说「多热」，没有一个字说「**这份报告里写了什么**」。
  而收藏一份报告的理由几乎总是「里面那几条动态我要跟进」，热度说明不了这件事。
- **动态卡**：只有标题 + 摘要。情绪（模型已经标好并存进 payload 了）没人用；
  想核对原文还得先回报告页翻到那一条 —— 一条被收藏的新闻，**在收藏页里读不到原文**。
- **名言卡**：只有一句悬空的「原句」。收藏这句话时读到的**场合与含义**（报告里给了 `background` / `note`）
  压根**没有落库**，于是收藏夹里只剩一句无出处的话。meta 行也缺媒体名。

**做法**（`utils/favorites.ts` + `components/favorites-view`，v3）：

1. **报告卡补「内容摘要」**：新增纯函数 `reportDigestOf(report)`，从 `report_cache` 摘两行 ——
   `最新`（**优先取 `coverage.latest` 的博查原值**，取不到才退回模型写的动态；日期是 `yyyy-mm-dd` 字面量，
   字典序即时序，**没有日期的条目不参与比较**）+ `素材`（`素材 N 条 · 近 7 天 M 条`）。
   与走势条**共用同一次批量读库**（`loadTrends` → `loadReportExtras`），**不额外花读请求**；
   仍**只认版本一致**的快照，否则会出现「热度是旧的、内容是新的」这种张冠李戴。
2. **动态卡补情绪标记 + 原文入口**：`SENTIMENT_TAG` 只列**偏离中性**的两档（积极 / 消极，措辞沿用报告页
   `SENTIMENT_META`）—— 中性是落库默认值，每张卡挂一个「中性」只是噪音；「原文」走的是与报告页
   **同一个**跳转出口 `utils/source-link`。**不加「复制链接」**：预览页里已经有了，同一条内容不需要两个入口。
3. **名言卡补快照字段**：`favoriteQuote` 的 payload 增 `background` / `note`（老收藏没有这两个键 → 归一成空串）；
   meta 行补媒体名（`context` 说「什么场合」、`source` 说「谁报道的」，合起来才核对得上；
   旧兜底值「据公开资料」等于没信息，不占这一行）。

**共同口径：取不到就不渲染，不给占位文案。** 摘要缺字段就少一行、名言缺背景就少一段，卡片退化成改版前的样子。
占位文案（如「暂无内容」）在真机上会被读成「这里本来有东西，是你们坏了」——
收藏页全是用户自己挑出来的东西，更不能出现这种痕迹。

**⚠ 命名坑**：payload 里的 `note`（报告给的名言注解）与本项目**已删除的顶层 `note` 列**（用户自写备注）重名，
两者无关，已在代码注释里点明，避免下次改版把它当成旧字段清掉。

**代价**：**0 额外读请求、0 新增依赖、0 新增页面 / 组件**（报告摘要复用走势条那次批量读）。

### O-24 AI 提问次数「好像没有计数」：把「数字」与「说辞」拆开 ✅

**问题**（用户 2026-10-08 反馈）：调试开关打开时，AI 提问用量**永远停在 0** ——
「我的」页的套餐用量卡与问答面板头都像坏了一样。根因是 `utils/qa.ts#qaRemainingToday()`
在开挂时**直接报满额**（注释给的理由是「照实相减会显示『还可问 0 次』却仍能一直问，自相矛盾」）。

这个取舍本身不算错，但它**把计数一起藏掉了**：同一张卡上，「生成」额度走的是另一条路
（`peekGenerateQuota.used` 照实报），于是两行用量「一行会涨、一行不会」——
在用户眼里就是「**AI 提问没有计数**」。

**做法**：把**数字**与**说辞**拆开，各自只负责一件事 ——

- 新增 `QaUsage { used, limit, remaining, unlimited }` 与纯函数 `qaUsageOf(used, member)` / `qaUsageToday(member)`：
  `used` 始终是镜像**真值**（负数 / NaN / 小数一律归零，页面**不自己相减**）；`remaining` 照实相减，
  但**在开挂态不再代表「还能不能问」**；要不要说「限制」由 `unlimited` 决定。
- 界面按 `unlimited` 二选一措辞：问答面板头「今日已问 N 次（调试模式不限次）」/「今日还可问 N 次」；
  「我的」页「已用 N 次（调试不限次）」/「已用 N / M 次」。
- **升级提示在开挂态一律不弹** —— 此时并没有被拦，弹「开通会员」是骗人。
- 旧名 `qaRemainingToday` **删除**：它唯一的语义就是「报一个会撒谎的数」，留着必然被下次改版再复制一遍
  （这个取舍已经在两处界面复制过一次了）。

**口径重申**：调试开关放开的**只是闸门**，**不是计数** —— 云端照读、镜像照抬、界面照实报。
排查时最需要的证据就是真实用量，把它藏起来等于把开关变成眼罩。

### O-25 报告页会员促销条：会员去噪 + 免费瘦身（压成单行） ✅

### O-26 报告页会员促销条：免费用户可关闭 + 随机展示（降频） ✅

**问题**（用户 2026-10-08 反馈）：「免费用户可以关闭，随机展示，不一定每次都展示」。

而一旦养成无视，报告页其它说明也会一起被无视。

**做法**（两件事，都是把它从「必看」变成「可选」）：

- **可关闭**：条子最右侧加一个灰色 ×，点它本机记住（`utils/member.ts#dismissPromo`），此后不再出现。

  - 关闭键必须 `stopPropagation`：整条是可点区域，不拦住就成了「想关广告，反被广告带走」；
  - 关完给一句 toast（「已关闭，不再出现」）：否则用户下次没见到它时会怀疑是坏了，而不是庆幸；
  - 「清空我的数据」把这枚记忆一并复位（`utils/settings.ts#clearLocalSettings` 调 `clearPromoDismiss`）——
    清数据是想要一个干净的开始，此时还留着「别看广告」既不在他的预期里，
    也没有任何入口能让他想起来去关。
- **随机展示**：`utils/member.ts#promoRoll(present, rand)` 掷骰子，概率分两档 ——
  **有专享段 70%**（这是服务性说明：你正在读一份被裁剪过的报告，而且开通后真的看得见那几段），
  **无专享段 30%**（纯招揽 —— 此刻没有任何东西被藏起来，偶尔提一次就够）。
  - 骰子**一次访问只掷一次**（`pages/report` 的 `promoRolled` ref 记住已掷过的 `personKey`）：
    每次重渲染重掷的话，条子会随机闪现又消失，看着像渲染 bug 而不是「随机展示」；
    「刷新最新」后仍是同一 `personKey`，沿用第一次的结果。
  - **会员不掷**，且掷骰子要等 `memberReady`：那之前 `member` 还是初值 `false`，会把会员当免费用户掷一次。
  - `rand` 可注入是为了用例：概率写反（30% 与 70%）肉眼要跑几十次才像，
    用例用 0 / 1 / 两档中点各钉一次。

**没做**：没有做成「每份报告各自记住关没关」（按报告逐份重新出现等于没关）；
也没有给「有专享段」那一档豁免随机 —— 它虽然更值得说，但仍然是一句广告，
豁免随机就退回了 O-25 之前「每份报告都出现」的状态。

**验证**：`npm test` **通过 216 / 216，失败 0**（促销条套件 4 例 → 6 例：

### O-12 「AI 提问」体验升级：个性化引导 + 引用可核对 + 新鲜度提示 ✅

**问题**（2026-10-07 复查，四处都指向「问答还是个半成品」）：

- 报告陈旧无提示：语料是报告快照，生成两个月后用户仍会拿它当「现在」来问。

**落地**：

- **个性化建议问题**（`utils/qa.ts`）：按该报告**实际具备哪些段落**生成候选（动态 / 观点 / 立场话题 /
  时间线 / 素材画像 / 报告评价 / 负面报道 / 热度），上限 8 条；**前三条顺序保持不变**（观感与改版前一致）。

  解析成「文字 + 引用组」；**越界编号不解析** —— 模型编造的编号留在正文里当普通文字，
  不指向一条不存在的来源（**编一个假出处比不给出处更糟**）。
- **来源行**：回答下方列出真正被引用到的素材（`[n] 媒体名`），带链接的走 `pages/link-preview`
  （与报告页同一落点），没链接的就地弹摘要；模型没标编号时退化为「依据 N 条报告素材作答」，不硬凑。
- **回答可复制**：长按回答气泡 → `setClipboardData`（用户经常要粘到别处）。
- **新鲜度提示**：会话头部改显示 `fromNow(generatedAt)`（如「3 天前生成的报告」）；生成 ≥14 天时

- **选人条升级**（`pages/ask` + `index.scss`）：首字头像 + 领域色（与关注流 / 收藏页同一套色）+
  「N 天前 · N 条素材」；候选 > 5 位时出现过滤框（只过滤本机已有报告的这批人，不做云搜索 ——
  搜到一个点不动的结果比搜不到更糟）；无匹配时说明「本页只能问已生成过报告的人」。
- 会话头部的报告名可点回报告页（问出兴趣后，下一步一定是看完整报告）；输入接近上限才显示 `n/120 字`。

**收益**：问答从「能问」变成「问得准、答得可核对、知道自己问的是哪一版语料」。
**代价**：回答长度不变（仍 200 字内），系统提示多一条规则；引用解析是纯端上字符串处理，
**无新增云读、无新增依赖、无新增页面**。
**真机验证点**：① 问一位报告较旧的名人 → 顶部出现新鲜度提示，点击回报告页；
② 回答里的 `[1]` 可点（跳原文预览或弹摘要）、长按气泡可复制；
③「换一批」确实换到下一组，且问题与该报告内容相关（话题名 / 素材条数）。

## 四、已评估但**不做**（记录取舍，避免重复讨论）

### O-8 候选列表加本机内存缓存（TTL） ➖

看起来能省掉切页重算，但与本页的设计取舍直接冲突：`pages/ask` 的 `useDidShow` 刻意「每次切回都重算」，
理由是**用户可能刚生成完一份新报告、或刚买完会员**，缓存会让「刚生成的报告不能立刻提问」。
若 O-1 之后仍有体感问题，正确做法是「**先渲染上一次的候选、后台静默刷新**」，
而不是整体 TTL 缓存（后者会把「新报告不出现」变成偶发 bug）。

### O-9 问答多轮记忆 ➖

**刻意不做**（`utils/qa.ts` 与设计方案同口径）：每次提问独立组 prompt、不带历史上下文 ——
一旦带上，界面就会让用户以为「AI 记得 TA 说过什么」，而语料本身只是一份报告快照，
这种错觉比「每次都要把话说完」的摩擦更贵。
