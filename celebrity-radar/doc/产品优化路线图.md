## 一、现状定位

一句话：**工程成熟度明显高于产品成熟度** —— 本质是「AI 深度尽调工具」，外面包了一层「看名人」的壳。

**定位已拍板（2026-10-16，D1）：转向「职业型工具产品」** —— 就是承认上面这句话，把壳从「看名人」换成「盯事」，
而不是继续给娱乐型消费产品补功能。含义、理由与反作用见 §7 D1。

| 维度 | 判断 | 依据（代码锚点） |
|---|---|---|
| 内容供给 | ★★★★☆ | 任意名人可查（联网检索 + 同名消歧），不是固定池；`requestChannel` 三层兜底 |
| 技术底座 | ★★★★☆ | 检索降级阶梯、厂商 × 质量档 × 能力槽（`llm.config.js`）、共享缓存 `report_cache`、全字段可溯源 |
| 合规完整度 | ★★★★★ | 同意网关 / 撤回同意 / 导出 / 注销 / PIPIA 留档已齐 |
| 留存设计 | ★★☆☆☆ | 只有每日订阅推送一条主动触达线（落点在 2026-10-16 修好，但**三枚模板当前尚未配置** ⇒ 这条线实际还没上线，见 §7 D3） |
| 变现结构 | ★★☆☆☆ | 卖「额度」，而额度的稀缺性会被共享缓存持续稀释 ⇒ **D1 已定方向：改卖能力 / 容量 / 导出（S3-1）**。第一件「与缓存无因果关系」的付费点已于 2026-10-16 落地（报告**结构化导出**，见 §4 商业层），但权益表主体仍是额度类，故评级暂不上调 |

## 二、已完成：S0 召回链路修复（2026-10-16）

### 2.1 问题

三个订阅消息云函数的 `page` 参数还是**分包改造前的旧路径**：

| 云函数 | 修正前 | 修正后 |
|---|---|---|
| `notifyFollowUpdates` | `pages/report/index?personKey=…` | `package/report/index?personKey=…` |
| `keywordAlert` | `pages/alerts/index?keyword=…` | `package/alerts/index?keyword=…` |
| `riskWatch` | `pages/alerts/index` | `package/alerts/index` |

要害在于：端上 10-14 分包后，小程序里**已不存在 `pages/report/index` 与 `pages/alerts/index`**，所以无论云函数是否重新部署，这两条推送都点不开 —— 这是全项目唯一的主动召回链路（关注动态 / 关键词预警 / 风险提醒三条定时推送），而订阅消息的授权是一次性的、很贵。

根因是**云函数与端上解耦**：端上路径改了，云函数这边不报错、不告警，只会静默失效。

### 2.2 修复内容

1. 三处 `page` 改为分包路径，各自留注释说明「必须与 `app.config.ts` 的 subpackages 一致」；
2. 全量扫过 `cloudfunctions/*/index.js`：写死的端上路径一共就这 3 处（`wxacode` 的白名单本来就是对的）；
3. **新增 `test/cases/52-route-params.js`** 补上真正的缺口 —— 云函数不在 tsc / 构建链路里，这类「另一处忘了改」此前没有任何东西拦得住。断言三条：
   - 云函数里出现的每个 `pages|x/index` / `package|x/index` 字面量，都必须能在 `app.config.ts` 的注册表里找到（注册表是唯一真源，不另抄一份）；
   - `subscribeMessage.send` 必须写死 `page` 且落点是注册路径（防「加了推送忘了写 page」；一处都没有、少于 3 处也会红）；
   - 注册表解析自检（避免检查退化成空跑）。
4. **端上兜底（参数缺失 / 非法不白屏）**：
   - 新增 `src/utils/route.ts#decodeParam`（唯一出口，解码失败退回空串）。原先 **7 个页面共 16 处**裸用 `decodeURIComponent(router.params.x)`，对非法百分号编码会抛 `URIError`，而 render 期间抛出就是**整页白屏**（转发被截断、小程序码 scene 残串都会带进来）；
   - `package/report` 缺 `personKey` 时原本给「生成失败 + 重试」——重试一万次也还是缺，是个走不出去的圈。改为专门的失效态：「这条链接没带上要看的人」+「去首页搜名人」（`switchTab` 回主包）；
   - `package/alerts` 核实过：未登录 / 无数据都有 `EmptyState` 兜底，不会白屏。

### 2.3 部署

三个云函数已 `tcb fn code update`（2026-10-16）。注意 `code update` 后代码不是立刻生效（实测约 15s 后才会跑新码）。

## 三、五个结构性问题

### ① 共享缓存会吃掉付费动机（最根本）

报告是全站共享缓存（`report_cache`，主键 `personKey = 名字#领域码`，命中的报告不再生成、不计额度）。结果反直觉：**产品越成功、缓存越厚，免费用户越撞不到付费墙**。

现在主要卖点是「生成额度」，但一个中度用户（一天查 2-3 个人）在缓存充足的今天根本用不完免费额度。**卖「用完即走」的东西，撑不起订阅制。** 这是产品层决策，调数值解不了。

**2026-10-16（S3-1）落下了第一件逆着①走的付费点：报告「结构化导出」（Markdown / JSON，`utils/report-export.ts`）。**
它不是一个额度 —— 报告已经在缓存里，导出只是纯本地组装（零上游成本、零等待、零额度），
而且**缓存越厚、能导出的报告越多，这一项越值钱**：把「缓存通胀」从贬值项翻成了增值项。
⚠ 但这只是一件：权益表主体仍是额度（见 §6.1 S3-1 的「没做」清单）。

### ② 日常打开的理由太薄

四个 tab：发现（工具型，用完即走）、提问（工具型）、舆情（唯一日常型）、我的。而舆情页要用户**先建立关注 / 监控**才不空 —— 新用户看到的是空态。产品里唯一「每天值得来」的页面，恰恰是冷启动最空的页面。

### ③ 撞墙时刻与付费理由错配

用户撞到额度的时刻，诉求是「我想再查一个名人」；产品给他的理由是「标准版 / 高级版模型、深度模式、多 2 节报告」。而端上设计上**用户根本看不到模型名**（只上报 vendor + quality，见 `llm.config.js` 的 `resolveLlm`）——「模型档位」这个卖点对用户几乎不可感知。**卖点在用户最不在乎的维度上。**

### ④ 内容消费没有「下一步」

报告读完 → 提问 / 对比 / 词云 / 分享，然后就结束了。缺的是：同类名人推荐、**「这段争议有新进展时提醒我」**、报告更新回访。而报告本身已经产出了「争议 / 风险」这些天然适合订阅的内容 —— 素材在手，却只做了一次性呈现。

**2026-10-16 进展**：前两项已做 —— 「这段争议有新进展时提醒我」＝ S1-1（争议点当监测词）；
「同类名人推荐」＝ S1-2（报告页尾，领域兜底 + 可就地关注）。**「报告更新回访」仍未做**，
且它不是端上能解决的：报告是全局共享缓存、只有用户点「刷新最新」才会重生成，云端并无
「按报告自动重生成」这一环 —— 要做得先补一条按报告维度的定时重生成 + 通知链路，另立条目再评。

### ⑤ 推送节奏一刀切

定时任务全部集中在清晨到上午（热门榜 6:30、关注动态 9:00、关键词预警 9:20、风险提醒 9:40、舆情聚类 10:00，见 `cloudbaserc.json` 的 triggers），而事件全天在发生。对用户来说，「今天该知道的」被压缩成早上一次，下午的热点要等明天。

**2026-10-16：问题判断不变，但解法被 D3 验证否决了一半**（结论见第七节 D3）——
「即时发」在当前授权模型下做不到：授权位是**布尔**（`users.subscribe_ok / alert_ok / risk_ok`，发一条就复位），
而授权只能由用户**点击**取得、发送时刻却由事件决定，两者天然不同步 ⇒ 一天里第 2 个高优先级事件必然无位可用。
更硬的是：**三枚模板在当前部署环境里都还没配置**（`config/public.ts`），连日报都还没发出去过。
所以「节奏」这件事**暂时不是端上能优化的**：先把模板开通、拿到真实推送数据（43101 比例、到达率），再谈分层。

**2026-10-16 追加：既然「时刻」暂不可动，那「推什么、推几条」这件事现在就定死**（口径见 §7 D4）——
顺着「一次授权一条」这条约束逐一核对三条链路，发现 `riskWatch` **违背了它**：
`notifyFollowUpdates` 每人一条（挑 `lead`，其余人数汇总进 `totalNew`）、`keywordAlert` 每人一条（取本轮新增最多的那个词），
而 `riskWatch` 是**按名人**发（`for (personKey) → for (watcher)`）—— 一个盯了 3 个人的用户会在同一轮里被 send 三次，
第 2、3 条**必然 43101** 并落进 catch 只记一行 skipped，日志看起来「一切正常」，
用户的体感却是「我盯了 3 个人，只有一个人的提醒来了」。已修为**每人每轮一条**
（按「级别最高 → 媒体发布时间最新 → personKey 兜底」挑正文，其余留在预警页），新增用例 `60-risk-push-one-per-user.js` 钉住。
**「节奏」这件事的坑填掉一半之后，剩下的「时刻」才轮得到让用户选。**

## 四、优化方向

> 本节只描述方向与理由；**状态一律记在 6.1 任务台账**，不在此处重复标注，避免两处口径打架。

### 体验层（1-2 周，目标：提高「每次打开的价值」）

| 编号 | 任务 | 为什么值得 | 成本 |
|---|---|---|---|
| S1-1 | **报告的争议 → 一键「盯这条进展」** | 用存量内容换留存，最自然的订阅钩子；复用现成的 `keyword_watches` / `utils/keyword-alert.ts` | 极低 |
| S1-2 | 报告页尾补「同类名人」：相关名人为空时按**领域**兜底，可就地关注 | 解决 ④，给内容消费一条延伸路径；顺带修掉「相关名人为空 → 页尾什么都没有」 | 低 |
| S1-3 | `alerts` 页消费 `?keyword=`（定位条 + 高亮命中该词的分组） | 把 2.4 的死参数用起来，推送点进去更「对得上」 | 低 |
| S1-4 | 舆情页冷启动不空：新用户给出 2-3 个可一键监控的推荐（他查过的人 → 热门榜），**不是**自动预置 | 解决 ②，让唯一日常型页面不再开局即空 | 中 |
| S1-5 | 推送分层：高优先级事件即时发，常规汇总保留日报 | 解决 ⑤。⚠ 受平台限制：订阅消息是**一次性授权 + 每次推送需额度**，做「即时推送」要先确认授权模型撑得住 | 高（需先验证平台可行性） |

**S1-4 落地口径（2026-10-16，含 D2 结论）**：原提案「新用户进舆情页就替他预置 2-3 个监控」**被否**，
落地成「**给出候选、由用户点一下才建**」。否掉自动预置的三条理由（任一条都足以否掉它）：
①`utils/risk-watch.ts#monitorPerson` 的第一条异步是 `requestSubscribeMessage`，而微信只认**点击后的第一个异步调用**，
非点击触发的预置永远拿不到推送授权；而 `monitorPerson` 的既有取舍是「授权失败照常把监控建上」，
于是自动预置产出的是**哑监控**（用户以为盯上了，实际一条推送都不会来）—— 比空态更糟；
②「监控某人」免费档**只有 3 个额度**（`config/benefits.ts#OPINION_LIMITS.personWatchCount`），
自动预置正好一次占满，用户随后想盯自己关心的人就撞「超限，先取消一个再加」—— 开局即负债；
③冷启动新用户**没有任何个性化信号**（history / follows / watches 全空），「预置谁」只能按平台热度挑，
等于在一个他还没表达过兴趣的维度上替他把额度花掉。
所以：规则模块 `src/utils/opinion-pick.ts`（纯函数 + 一处本机 storage，不查库、不检索、不花额度），
候选**优先「他查过的人」**（`utils/history.ts#listRecentHistory`，冷启动场景里唯一可能的真实意图信号，
老用户回归也用得上），不足才用**热门榜**补齐（`utils/hot-board.ts#loadHotBoard`，带静态种子兜底、永不为空）；
去重按 `personKey` **和**人名两个维度（同名不同领域是两份报告，但对用户就是同一个人，并排两个「张三」只会让人以为页面错了）；
已监控的人不再进候选。数量 `PICK_LIMIT = Math.min(3, personWatchLimit(false))` —— 推荐量**不许超过免费档能建的量**，
否则就是在推销额度；候选不够如实少给、不硬凑。四条硬约束：
①**来源与代价都写在点击之前**（`pickSourceNote` / `pickCostNote`）：不许写「你可能认识 / 为你精选」这类暗示平台懂你的话 ——
冷启动的新用户没有个性化信号，这些名字就是平台按热度挑的；说清来源用户才有理由拒绝。
`pickCostNote` **不写死「免费版 3 个」**：舆情页是**不引入会员态**的页面（用例 36 钉住的形态锁），
写死档位数字对会员就是错的，只说「有上限、超了要先取消」则两档都成立。
②**关系数只在「读数据那一刻」判一次**（`shouldShowPick`），判完把候选存进 state，**不在渲染期用实时关系数再判**：
用户从卡里建掉第一个之后关系数就 > 0，实时判定会让卡在「还剩两个候选」时突然消失；关系数**算不出来时返回 false**
（给一个可能已经有关系的用户推「先盯上几个人」，比少推一次难看得多 —— 与 `isColdPerson` 同一取舍）。
③**关掉就永久不再出现**（本机键 `opinion:pick.dismissed`，与 `inbox:seen` 同类）：它是给新用户的引导、不是常驻推荐位，
用户明确说了不用就别再问第二遍；该键在「清空我的数据 / 注销 / 撤回同意」三条清理路径里一并清除。
④**不破坏本页既有的两条形态锁**：不引入会员态变量（R2 用例 36）、不引入弹窗（用例 29）——
建立失败**就地一行全文显示**（`res.fatal` 那种长文案走 toast 会被截成半句，等于没说），
且卡片另起 `page-opinion__pick*` 类名而**不复用** `page-opinion__more`（后者被用例 36 / 39 钉死为「全页只剩事件卡一处」）。
卡片放在**简报之前**：新用户的简报四格全是 0，那一屏上唯一能做的事就是这张卡。

### 增长层（1-2 月）

| 编号 | 任务 | 说明 |
|---|---|---|
| S2-1 | 分享对象升级：从「分享一份报告」到**「分享我正在盯的人」** | 点进来直接可关注，比分享结论更接近增长闭环；可复用 `utils/share.ts` / `share-code.ts` 现有能力 |
| S2-2 | `profile` 页加一键「关注 / 监控」 | 现在要先绕到报告页 / 舆情页才能建立监控关系，而「读到这个人 → 想盯着他」正好发生在名人主页，同一次决策却要换两个页面 |
| S2-3 | 首建激励：第一个为某位冷门名人建立报告的用户给可见回报 | 呼应现有「为全站建立」的提示，把「冷门人物也值得建」变成用户动机 |

**S2-1 落地口径（2026-10-16）**：分享框**随分享者与这个人的真实关系换**，而不是给所有人换一句话。
关注了 TA 的人转发 / 分享到朋友圈，出去的是「我在盯张三｜1 处公开争议」（后半句一字不改，仍是
可在报告里逐条核对的钩子）；没关注的人仍是「张三 · 科技｜…」—— **不许替用户编造「我在盯」**，
那句话对方点开一核对就露馅。落地页（报告页）靠 `?from=watch` 认出这次是好友分享，在人物横幅
**之上**给一条「朋友在盯 X」+ 一键关注：它不受「报告是否生成」影响（关注只需要 personKey，
不必先等那 30 秒），且等关注态读过一次才渲染（已经关注的人不该被劝「快关注」）。
三条硬约束：①标题与落地路径由 `personShare` **成对产出**（只改一半 = 标题说我在盯、路径没标记，
引导永远不出现，而分享侧看起来一切正常）；②落地标记只有 `utils/share.ts` 一处真源，页面只准调
`isWatchShare`；③关注仍走唯一写库口 `utils/follows.ts#toggleFollow`，来源标 `watch_share` 只进埋点。
可归因口径：`share`（`frame='watch'|'report'`）× `watch_share_arrive` × `follow`（`from='watch_share'`）。

**S2-2 落地口径（2026-10-16）**：名人主页头部独占一行的「监控风险」（**不挤进「深度报告 / + 关注」那行胶囊按钮**）——
三个等宽按钮里「+ 监控风险」会被挤成省略号，缩成「+ 监控」又与「+ 关注」分不清，而这两件事语义完全不同：
关注是记一笔（看动态汇总），监控是让云端**每天替你检索一次公开报道**。所以这行先写明代价（每天一次检索、
命中风险词才记一条信号、可在预警页查看或取消），再让用户点。三条硬约束：①**授权顺序**：微信只认点击后的
第一个异步调用，`monitorPerson` 内部第一条就是 `requestSubscribeMessage`，故页面在这行之前不能有任何 `await`
（插一次查库就会让订阅框从此不再弹、且不报错）；②**按钮态必须读真实监控名单**（`listPersonWatches` +
`isMonitored`），不能按「报告页才建过监控」假设成未监控 —— 否则两个入口对同一个人给出两个答案；③链路一行不新造
（仍走 `utils/risk-watch.ts` + `keyword_watches` + `riskWatch`），**关系类动作在唯一写库口埋点**（与
`utils/follows.ts#toggleFollow` 同一约定）：`monitor_add` / `monitor_remove` 带 `from`（`'report'` / `'profile'`
/ `'alerts'`），用来回答「不必再绕路之后，监控到底从哪建立的」。

**S2-3 落地口径（2026-10-16）**：先把「激励谁」定死 —— 不是所有首建者，而是**冷门人物的首建者**。
热门人物早有人建过，首建多半轮不到你；真正没人愿意花额度去建的是**公开报道很少的长尾人物**，
第一个建的人补上的是库里长期空着的一个位置。三条口径：
① **冷门判据只认素材条数**（`utils/report.ts#isColdPerson` 看 `coverage.items ≤ coldItemsMax`，
线在 `config/benefits.ts`）。不用热度 / 热榜反推 —— 热榜只收热门的人，拿「不在榜」当冷门等于激励人人有份。
缺 `coverage` 的老报告**一律不算冷门**：这是授予荣誉的判据，宁可少说一句，也不能凭一个缺失字段许一句兑现不了的话。
② **判在写库那条路径上**（`utils/cache.ts#finalizeAndReturn`），与埋点同源；页面只负责渲染，
不自己在渲染期重算一遍（否则「页面说你是第一位」与「埋点说不是首建」迟早对不上）。
③ **荣誉的兑现物就是那句话本身，不加码**：复用同一个 notice key（`firstBuild`）换一套文案（不新造提示条），
明说「TA 的公开报道不多（本次 N 条素材）」把「为什么是你」说清，**不写**「免计费 / 送次数」——
那笔账由 `quotaGuard` 复核、端上给不了准话。配套把「冷门人物首建率」变成可观测项：
`report_generate` 补 `cold` 与 `materials`，且**每次生成都报**（率需要分母）。

### 6.4 S3 的前置决策

**D1 已拍板（2026-10-16）：职业型工具产品** —— S3-1 / S3-2 / S3-3 解阻塞，可以开工。
三条落地口径（都从 D1 这张表直接推出来，不是新主张）：
①**付费项必须与共享缓存无因果关系**（S3-1）：`report_cache` 是全局共享的，卖「生成次数」等于卖一件
会随缓存变厚而自动贬值的东西；能卖的是**容量与能力**（监控人头数、提醒优先级、导出、历史版本、协同）。
②**入口仍是「查人」，但主线动词改成「盯事」**（S3-2 / E1）：报告是获客钩子，付费发生在「持续盯着」上 ——
这也与 `opinion_events` / `keyword_watches` / `risk_watch` / 周报这批已有资产同向，不必新造管道。
③**分档呈现而非分档生成**（S3-3，2026-10-16 已落地）：共享缓存决定了「同一份报告只能生成一次」，
所以免费 / 会员的差别只能落在**看得到多少**，不能落在「生成两份」。
**「看得到多少」必须同时是两个杠杆**（只做一个，观感差异都出不来）：
**看得到哪几节**（`report-toc.ts` 的 `tier`：免费 11 节 / 会员 18 节）+ **每节能看多少条**
（`config/benefits.ts#REPORT_PREVIEW`：免费每节 3 条 / 会员不截断）。
第一版只动节数（16 节 / 会员多 2 节），免费档每节仍是完整长度 ⇒ 免费用户看到的是「少两节但每节都很长」，
与会员的观感几乎一样 —— 差量偏小不是「节数不够多」，而是**杠杆用少了一个**。
配套：截断只发生在渲染那一行（数据原样完整，换人 / 换页 / 导出都读到全量），
且每处截断**就地写出「还有 N 条」**（静默截断等于让用户以为这已经是全部）；
会员节在免费档**本来该在的位置**渲染锁态卡（节名与说明取自模板真源，不剧透内容）。
④**「看得到」与「带得走」是两档，不是一档**（2026-10-16 S3-1 落地的口径，从①②直接推出）：
站内阅读免费（那是入口），**把报告变成能进自己文档 / 表格的东西才是付费能力**（长图 / Markdown / JSON）。
这条同时解决了①的一个副作用 —— 免费能读到全文（共享缓存决定的），但「带走」永远不共享：
同名报告全站只有一份，但每个人带走的那份是各自组装的，所以它不会随缓存变厚而贬值。
执行上沿用既有先例（`canExportReportCard` / `canExportWeeklyBrief`）：**免费看得见入口 + 一行非弹窗引导**，
不藏按钮（藏起来用户只会以为没有这个功能，而不是发现这是会员能力）。

⚠ 定位转向的**反作用**（已做的功能里偏娱乐型的部分，别再用「用户量」给它们加码）：
分享钩子（S2-1）、冷启动推荐（S1-4）、冷门首建激励（S2-3）本质都是**消费型增长手段**，
在职业型定位下它们仍是有效入口，但**不该再作为主线继续投入** —— 职业用户的留存来自「不漏事」，
不来自「分享得好看」。这不表示要回滚（都已上线、成本已沉没），只是排期上让位给 S3 与 E1。

### 6.5 度量方式

- 现有埋点通道可用（如 `track('report_qa_ask')` 一类），新增动作应同时埋点，否则事后无法判断
- 关注指标：推送点击到达率、次日 / 7 日回访、监控建立数、报告页「下一步」点击率
- 监控指标（S2-2）：`monitor_add` 的 `from` 分布 + 按人建立的监控数 —— 它回答的是
  「读到一个人就想盯着他」这个动作发生在哪一页（`'report'` vs `'profile'` vs `'alerts'`），
  而不是「监控按钮被点过几次」（后者分不清是建立成功还是被上限拦下）
- 分享指标（S2-1）：`share`（`frame='watch'|'report'`）→ `watch_share_arrive` → `follow`（`from='watch_share'`）
  这一跳的比例 —— 它回答的是「陌生人顺着人际链进来看得懂、愿意留下吗」，
  而**不是**「分享按钮被点了多少次」（后者只说明分享文案好看，不说明有人留下）
- 首建指标（S2-3）：`report_generate` 的 `cold` × `firstBuild` × `materials` 三个维度 ——
  冷门人物首建率 = 冷门且首建的生成数 ÷ **全部生成数**（不是 ÷ 首建数）。因此 `cold` 与 `materials`
  必须对**每一次**生成都上报：只报首建就只有分子、永远算不出率。`materials` 顺带是调冷门线
  （`config/benefits.ts#reportSource.coldItemsMax`）时重算真实分布的原始数据，不必再等一批埋点
- 冷启动指标（S1-4）：**分子是 `monitor_add`、分母是 `opinion_pick`** ——
  分母于 2026-10-16 补齐（原先只有分子，**算不出转化率**）：
  · 分子：推荐里点建的监控走既有的 `monitor_add` 且 `from='opinion'`（`utils/risk-watch.ts`
    只在**真的建成**时才报，超限 / 授权失败不入账）；
  · 分母：`opinion_pick`（舆情页 `loadPick` **真的设入候选**时上报，带 `count` 候选数与
    `history`「他查过的人」条数）。**只在候选非空时报**：关过 / 有关系 / 算空都不报，
    否则分母里混进「这张卡本来就没显示」，转化率被系统性低估（同 `report_export` 的口径）。
  两条的比才是 S1-4 的效果。**别拿 `monitor_add` 的绝对条数当效果**（它分不清是冷启动推荐建的，
  还是老用户在预警页加的 —— 只靠 `from` 分得清入口，分不清是不是新用户）。
  `history` 顺带是那条优先规则的体检指标：恒为 0 就说明「他查过的人」这个分支在实际流量上从没命中过
  （此时该查的是历史记录那个读口有没有真的给到数据，而不是继续加推荐位）。
- 推送粒度指标（S3-4，**不需要新埋点，云函数回执里就有**）：`pushed` ÷ `users` ——
  分子是「真正发出去的条数」，分母是「有监控关系命中的用户数」。这个比值就是**授权健康度**：
  趋近 1 说明用户手上的授权位是够的；明显小于 1 则说明大量用户授权已耗尽（`skipped` 里的 43101 会同步变多）。
  ⚠ 这两个数回答的问题不同，**不能混着看**：`users` 是影响面（含没授权的人），`pushedUsers` 是被打扰的人数。
  修复前 `riskWatch` 的 `pushed` 会小于「命中人数」，但日志里没有任何异常 —— 所以这条指标要**连着 43101 比例一起看**，
  只看 `pushed` 的绝对值永远发现不了「有一半提醒被静默丢弃」。
- 导出指标（S3-1，`report_export` + `report_exported`）：**两个事件配对才成立** ——
  `report_export`（`kind='card'|'data'`，含 `allowed:false`）回答「哪个出口有人真想用、有多少需求正好撞在墙上」，
  `report_exported`（`kind='markdown'|'json'`）回答「带走的形态是哪种」。
  要看的比是 **`allowed:false` ÷ 全部 `report_export`**（付费墙的命中率 = S3-1 的转化分母，
  要拿去和 `payCreate` 对）以及 **`report_exported` 里两种格式的占比**（只被选一种 = 另一种白做）。
  ⚠ 埋点在**判身份之前**：只报放行的话分母消失，「没人想导出」和「墙太靠前」就永远分不清。
  这与 §6.5 开头那条是同一个要求 —— 长图导出 2026-10-15 上线时漏了埋点，本次一并补上。
- 不建议在 S1 就引入归因模型，先把「动作有没有发生」记准

### D1 对比：继续做「娱乐型消费产品」，还是转向「职业型工具产品」？

| | 娱乐型 | 职业型 |
|---|---|---|
| 用户 | 大众，好奇驱动 | PR / 媒体 / 投资 / 猎头 |
| 核心动词 | 查人 | 盯事 |
| 付费点 | 内容解锁、次数 | 监测容量、导出、协同 |
| 与共享缓存的关系 | 冲突（缓存越厚越难转化） | 相容（缓存是入口，容量与能力是付费） |
| 现有资产的复用度 | 中 | 高（`opinion_events` / 监控 / 周报 / 导出均已存在） |

两个方向的付费设计完全不同，越早定越省事。**从现有资产看，职业型方向的杠杆明显更大**。

### D1 结论（2026-10-16 拍板）：选**职业型工具产品**

不是「再做一个版本」，而是**承认产品已经是这个东西**：工程侧现有的全部重资产 ——
全字段可溯源（`report_cache` 的每条素材都带出处）、`opinion_events` 事件聚类、`keyword_watches` / `risk_watch`
两套持续监测、周报 / 历史 / 导出、厂商 × 质量档的成本闸门 —— 指向的都是「可核对的持续尽调」，
而不是「看名人」。娱乐型定位下，这些能力**每一条都要重新解释一遍用户为什么需要**；职业型定位下它们就是主线。

**选它的三条理由**（按权重）：
①**付费与共享缓存相容**（决定性）：`report_cache` 是全局共享的，同一份报告全站只生成一次 ——
在娱乐型定位下，卖「生成次数」等于卖一件**会随着缓存变厚而自动贬值**的东西（这也是 §1「变现结构 ★★☆☆☆」的成因，
结构性矛盾，靠调额度数字解决不了）；职业型的付费点是容量 / 导出 / 协同，缓存越厚越接近「免费获客的入口」。
②**资产复用度**：S3-2 要的多人面板、事件跟踪、导出，底层已经全在了；娱乐型要做的是「更多名人、更好看」，
反而要新造内容池。③**「事件」比「名人」更接近付费场景**：愿意为一件事的进展付费的人，
比愿意为一个名人的报告付费的人多得多，也更容易续费。

**代价（要认）**：职业型的天花板是**用户量小**，且需要「监测准确性」兜底 —— 漏报一次比误报十次更伤专业用户。
所以下面的顺序不能颠倒：**先把推送这条唯一的触达链路真正跑通（三枚模板开通 + 每人一条），再谈工作台**。
一个会漏事的监测工具，卖不出工作台。

### D3 结论：推送「即时送达」（2026-10-16 验证，结论 = 现状下不可行）

**验证方法**：把现行三枚订阅消息链路的授权模型、数据结构、定时器配置逐条读出来对「即时推送」的要求，而不是引用平台文档下结论（平台规则会变，代码锚点不会）。

| 事实 | 代码锚点 |
|---|---|
| 授权位是**布尔**，发一条就复位 | `dbInit/schema.js` 的 `f('subscribe_ok','boolean',{def:false})` / `alert_ok` / `risk_ok`；三个推送函数发完即 `update({ data: { risk_ok: false } })`（`riskWatch` / `keywordAlert` / `notifyFollowUpdates`），注释里写明「一次授权一条，不复位下次必得 43101」 |
| 一枚模板一位授权，**三枚不能合并** | `config/public.ts#alertTemplateId` / `riskTemplateId` 的 ⚠ 段：按模板消耗授权，共用必然 43101 |
| 授权只能由**用户点击**触发 | `utils/notify.ts` 三处 `requestSubscribeMessage` 前的注释；`utils/risk-watch.ts#monitorPerson` 把授权排在第一条 await |
| 每个渠道**每天只跑一次**定时器 | `cloudbaserc.json`：09:00 / 09:20 / 09:40 各一个 `timer` |
| **三枚模板目前都没配** | `config/public.ts` 三处注释：「功能完整保留、当前部署环境未配置」⇒ 授权按钮不渲染、云函数记录并跳过推送 |

**结论**：不可行，且不是「平台不允许」，而是两处自身约束叠加：
①**数据模型表达不了「攒授权」** —— 用户点 5 次授权，`risk_ok` 也只记得「有 1 位」；
②**发送时刻与授权时刻天生不同步** —— 即时推送要在事件发生的那一刻手上还有授权位，而授权只能由用户在
「主动建监控 / 开提醒」时给（一天可能一次都没有）。第 2 个高优先级事件必然无位可用，直接落到 43101。

**三条出路（都要前置，不能直接开工）**：
1. **长期订阅**：类目白名单制（政务民生 / 医疗 / 金融 等），需在公众平台确认本项目类目够不够格 —— **只能外部确认**；
2. **把授权位从布尔改成计数**（`*_ok: number` + 每次发送扣 1 + 端上「续订」入口）：技术可行，但要动
   `schema.js`（类型变更 + 存量布尔迁移）、三个推送函数、端上 `notify.ts` 三处，以及**所有** `where({*_ok: true})`
   查询；而且「用户为什么要攒」这个问题在「一天最多发 1 条」的现状下没有答案 —— 记在账上，等有推送数据再谈；
3. **用户可选推送时段**（本文件预设的 fallback，也是**推荐的下一步**）：保留日报，只把「几点发」交给用户。
   代价要说清：定时器在服务端固定（`cloudbaserc.json` 的 cron），要支持自选时段就得**一天多跑几轮**、
   每轮只发给选中该时段的人；若不做按轮次裁剪检索面，上游检索成本就是 × 轮数。

**真正的第一步（运维动作，不是开发）**：先按 `config/public.ts` 的三步开通三枚模板（各含 `thing1` + `date2`、
**必须三枚不同**），发一周真实推送，看 43101 比例与到达率 —— 在「一条推送都没发过」的阶段调推送节奏，
调的是猜测。

### D4 结论：推送「推什么、推几条」（2026-10-16 拍板，问题由上面的 D3 引出）

D3 证明「即时发」做不到，于是「节奏」只剩两个可动的变量：**时刻**与**每轮条数**。
时刻要动就得改 cron / 改成本结构（且当前零推送数据），所以**这一轮只动条数**：

- **口径：每人每轮每条链路最多一条**。依据不是「省着用」，而是**授权模型本身**：
  `users.*_ok` 是布尔、一次授权只够一条，第二条必然是 43101。
- **三条链路现状**：`notifyFollowUpdates` ✅（每人一条，挑 `lead`）、`keywordAlert` ✅（每人一条，取新增最多的词）、
  `riskWatch` ❌ **按名人发** —— 一个盯了 3 个人的用户同一轮被 send 三次，第 2、3 条必然 43101 并被静默计入 `skipped`。
  已修为每人一条（**已部署**）。
- **挑哪一条上正文**：级别最高（`LEVEL_RANK`）→ 媒体发布时间最新 → `personKey` 兜底。
  ⚠ 兜底不能省：同级别且都没发布时间的命中很常见，不稳定排序会让「谁上正文」每轮都变，用户看到的是随机内容。
- **信息不能丢**：正文报「N 人出现风险，最严重「X」类别」，其余留在预警页（`package/alerts` 看得到全量）。
  ⚠ 文案要**先算长度再定句式**：`thing1` 上限 20 字符，第一版写的「N 个监控对象出现风险，最严重：「张三」司法监管」
  是 21 字，被 clamp **从尾部切掉**，切掉的正好是「类别」—— 这是本条的唯一一次返工，用例已钉住 20 字符与「不许出现省略号」。
- **明确不推的**：`low` 级别只落库（`PUSH_LEVELS = ['high','mid']`，既有取舍）；热门榜只做站内，永不进推送
  —— 娱乐向内容不该占用职业用户手里那一条授权。
- **时刻暂不动**（理由见 §3 ⑤）：改为「模板开通 + 拿到一周真实数据」之后的独立决策；
  自选时段要按轮次裁剪检索面，否则上游成本 × 轮数。
