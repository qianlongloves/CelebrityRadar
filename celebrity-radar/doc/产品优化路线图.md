## 一、现状定位

一句话：**工程成熟度明显高于产品成熟度** —— 本质是「AI 深度尽调工具」，外面包了一层「看名人」的壳。

**定位已拍板（D1，2026-10-16）：转向「职业型工具产品」** —— 就是把上面这句话认下来：把壳从「看名人」换成「盯事」，
而不是继续给娱乐型消费产品补功能（理由、代价与反作用见 §6 D1）。

| 维度 | 判断 | 依据（代码锚点） |
|---|---|---|
| 内容供给 | ★★★★☆ | 任意名人可查（联网检索 + 同名消歧），不是固定池；`requestChannel` 三层兜底 |
| 技术底座 | ★★★★☆ | 检索降级阶梯、厂商 × 质量档 × 能力槽（`llm.config.js`）、共享缓存 `report_cache`、全字段可溯源 |
| 合规完整度 | ★★★★★ | 同意网关 / 撤回同意 / 导出 / 注销 / PIPIA 留档已齐 |
| 留存设计 | ★★☆☆☆ | 主动触达只有三条订阅推送，而**三枚模板至今未配置**（连日报都没发出去过，见 §6 D3） |
| 变现结构 | ★★☆☆☆ | 卖「额度」，而额度会被共享缓存持续稀释 ⇒ 已转向卖能力 / 容量 / 导出（S3-1）；但权益表主体仍是额度类，故评级暂不上调 |

## 二、五个结构性问题与当前状态

| # | 问题 | 2026-10-16 状态 | 归属 |
|---|---|---|---|
| ① | **共享缓存会吃掉付费动机**（最根本）：报告是全局共享缓存（`report_cache`，主键 `personKey = 名字#领域码`），命中的不再生成 ⇒ **产品越成功、缓存越厚，免费用户越撞不到墙** | 已落下第一件逆着它走的付费点：报告**结构化导出**（纯本地组装，缓存越厚能导出的反而越多）；**报告历史版本**同理（旧版被覆盖即永久消失，把它变成可回溯） | S3-1 |
| ② | **日常打开的理由太薄**：唯一的日常型页面（舆情）要先建关注 / 监控才不空 ⇒ 每天值得来的页面恰恰冷启动最空 | 冷启动给「点击式」候选（不自动预置）；「我盯的事」有新进展会进日报 | S1-4 / E1-① |
| ③ | **撞墙时刻与付费理由错配**：用户撞额度时想的是「再查一个」，产品答的是「模型档位 / 多几节」—— 而端上**根本不显示模型名** | 分档呈现（免费 / 会员观感差异做出来）+ 能力项（导出：长图 / 周报图 / 结构化数据；历史版本文本） | S3-3 / S3-1 |
| ④ | **内容消费没有「下一步」**：读完报告 → 提问 / 对比 / 分享，然后就结束了 | 「争议→盯这条进展」与「同类名人」已做；**「报告更新回访」已做**（N-2，站内版：消息中心多一类「你上次看的这个人报告更新了」） | S1-1 / S1-2 / N-2 |
| ⑤ | **推送节奏一刀切**：定时任务集中在 6:30~10:00，而事件全天在发生 | 「即时发」经 D3 验证**不可行**；改为先把**条数口径**定死（每人每轮每条链路一条）；**时刻暂不动** | S3-4 / S1-5 |

⑤ 的两条追加结论（都是被验证压出来的，不是偏好）：

- **「即时发」不是平台不允许，而是自身约束**：授权位是**布尔**（`users.*_ok`，发一条即复位），
  而授权只能由用户**点击**取得、发送时刻却由事件决定 ⇒ 一天里第 2 个高优先级事件必然落到 43101（见 §6 D3）。
- **先修条数口径，再谈时刻**：`riskWatch` 原按名人发，第 2 条起注定发不出去、且**静默**（只记一行 `skipped`），
  用户体感是「我盯了 3 个人，只有一个人的提醒来了」。顺序反过来就会在「一条推送都没发过」的阶段调猜测。

## 三、优化方向（为什么这么做）

四个方向层**并行不冲突**，但**同一时间只动一层**：改体验层的判据在端上（看埋点与回访），改商业层要先有留存，
方向混着推会出现「功能都做了、归因说不清」。

### 3.1 S1 体验层：让「没有任何新事发生」的这一刻也有内容

| 编号 | 方向 | 判据（怎么算做到了） | 反向约束（明确不做） |
|---|---|---|---|
| S1-1 | **争议 → 盯这条进展**：把「看热闹」接成「订阅一件事」 | 用户能从报告/事件页一键跟进，跟进后有进展会推他 | 跟进**不等于书签**：详情页刻意**不自动标已读**，点了跟进也不许把角标吃掉 |
| S1-2 | 报告读完给**下一个可查的人**（相关名人 / 同类名人） | 报告底部有下一步入口，点进去就能查（**不要求已缓存**，本项目任意人名可查） | 不做「猜你喜欢」式推荐（没有协同过滤数据，做出来就是随机） |
| S1-3 | 关注动态页：「我关注的人各自有什么新东西」 | 冷启动不空、增量口径与角标一致 | 不在这一页重复放报告明细（明细指回报告页） |
| S1-4 | **舆情页冷启动**：给「点击式」候选，不自动预置（D2） | 新用户进页即有可看内容，且**没有**替他建监控/关注；候选卡真的出现过要留痕（`opinion_pick`） | 不代替用户点（预置 = 用他的额度给别人查） |
| S1-5 | 推送**节奏**：先条数口径（= S3-4），后时刻分布 | 每人每轮每条链路**至多一条**，失败必留痕 | 时刻暂不动；三枚模板未配置前，一切节奏讨论都是猜测 |

### 3.2 S2 增长层：分享出去要有「落点」

| 编号 | 方向 | 判据 | 反向约束 |
|---|---|---|---|
| S2-1 | 分享钩子：报告里挑**最能被转述**的一句做卡片标题 | 不同人/不同领域给出的钩子不重复、不剧透结论 | 钩子只搬运报告已有内容，不新造事实 |
| S2-2 | 分享码：扫码直达**这个人**的报告 | 长名字/特殊字符编不完时**退首页**，绝不截断到错的页 | 不在码里塞个人信息（openid 一律不进 scene） |
| S2-3 | 报告长图：给「截图发群」这件事一个正经产物 | 长图内容与报告一致、可离线看 | **敏感名单命中直接不出图**（宁可少一个传播，不可多一次事故） |

### 3.3 S3 商业层：卖**能力**，不卖**额度**

| 编号 | 方向 | 判据 | 反向约束 |
|---|---|---|---|
| S3-1 | 付费点从「多查几次」转向**导出 / 交付物**（D6）：长图 / 周报图 / 结构化数据；**历史版本（S3-1 ③）** 同属这一类 | 判据是**「付费项必须与缓存无因果关系」**：缓存越厚，这些能力越有价值 | 不卖「模型档位」给用户看：端上**不显示模型名**，用户要的是可用，不是参数 |
| S3-2 | **监测工作台**：横向看「我盯的几个人谁在动、能否一起写」 | 与预警页回答**不同的问题**、明细**不复制**只指路 | 站内看（面板/对比/事件跟踪）免费与会员**完全一致**（D7），只有导出是会员能力 |
| S3-3 | **分档呈现**：节数 + 每节条数**两个杠杆同时用** | 免费用户与会员用户看到的**观感差**一眼可辨 | 截断**只发生在渲染那一行**（数据原样完整，导出/换页读全量）；不剧透被锁内容 |
| S3-4 | 推送**条数口径**统一（D4，见 S1-5） | 不出现「静默只发第一条」 | 不为发满条数而降质（宁少勿滥） |
| S3-1 ③ | **报告历史版本**：被刷新覆盖掉的旧版可回溯（`REPORT_VERSION_KEEP = 5`） | 免费看**列表**、会员看**正文**；能回答「上个月这家公司你们怎么写的」 | 列表免费、正文收费（列表也收钱，用户连「有人刷新过」都看不见）；**不做跨人折算**、不给综合分（这是导出族的通用底线） |

### 3.4 E1 事件主线：从「看到事件」到「订阅事件」

| 编号 | 方向 | 判据 | 反向约束 |
|---|---|---|---|
| E1-① | 跟进的**事件**有新报道 → 进日报候选（D5） | 会员正文优先给「我盯的事」、免费档先给「关注的人」；**没告诉他的那条不记水位** | 跟进 ≠ 书签：详情页刻意**不自动标已读**，点了跟进也不许把角标吃掉 |
| E1-② | **事件级订阅**（按人 / 按话题订阅事件，而不只是跟进单条事件）—— ✅ 已完成（站内口径，见 §5.1） | 用户能订阅「这个人的所有事件」「这个话题的所有事件」：订阅 → 预警页「订阅的对象」+ 事件列表打标 | 不做「同一事件每天一条」：订阅不能绕过条数口径（S3-4）；**不另算一套角标**（命中的事件本就参与 `new` / `update` 判定，再算一个 = 同一件事提醒两次）；**满员不静默顶掉**最早订阅的那个 |

E1-① 的一条硬口径：**水位只在「真的告诉他了」时写**（推送失败不写、消息里没提到不写）——
写早了 = 这条提醒**永远消失**，而且没有任何报错。

## 四、拓展思路（不是计划，是备选池）

只记「想清楚了才动手」的几条；**没写进 §5 的都不算承诺**。

| 思路 | 为什么可能成立 | 前置条件 | 主要风险 |
|---|---|---|---|
| **事件级订阅**（E1-②）—— ✅ 站内部分**已完成**（见 §5.1） | 事件是唯一「全天在发生」的内容，也是唯一能自然触发推送的东西；按人/按话题订阅把「一次性查询」变成长期关系 | ~~三枚模板配置 + 条数口径（S1-5）先落地~~ ⇒ **不成立**：站内订阅与推送无关（D8），已先上线站内版 | 推送频次失控 ⇒ 被关掉整条通道，不可逆（**只对推送版成立**；站内版无此风险） |
| **批量尽调**（一份名单一起查） | 职业场景的真实用法是「这 8 个人能不能合作」，不是「查一个」 | 工作台（S3-2）已有跨人指标台账 | 名单越长越像「平台给结论」，合规口径要更谨慎 |
| **定时或导出交付**（周报文件/邮件） | 导出是**抗缓存贬值**的付费点（S3-1），可加自动化 | 导出已具备（本地组装） | 交付物离开 App 后失控 ⇒ 简报只搬运信号、不带评价类判断 |
| **话题 / 领域维度** | 领域码已在 `personKey` 里（`名字#领域码`），天然可聚合 | topic 页已在 | 聚合页容易变成「二次编辑」，要警惕变成媒体 |
| **B 端（剧组 / MCN / 品牌）** | 需求真实、付费意愿强、与现有能力同构 | 先证明 C 端留存成立 | 拉走产品重心，与 D1 的「职业型工具」定位先打一架 |

**明确不做**（写在这里，避免反复讨论）：

- 社交与 UGC（评论/打分/共建人物页）：要治理、要审核、与「基于公开信息 AI 整理」的免责口径冲突。
- 全网爬取与私域数据：检索只用已接的检索源，不碰私信/私域。
- 「平台综合评分」：一旦给分数就是替用户排序，责任与合规都不划算（S3-2 工作台里同样禁止跨人折算）。

### N-6 落点（2026-10-16）

**做的是「合并口径」，不是「删页」。** 先说为什么不删：`package/compare` 与 S3-2 工作台的
重叠**只有「指标对照表」这一块**，而它独有的是双人**共同关注点 / 情绪结构 / 公开立场对照 /
对比问答 / 「A vs B」分享路径**（对比页是那条分享路径的落点，长期获客的一环）。把它们一起删掉，
换来的只是少一个页面，代价是一条获客路径和四个能力 —— 那不是减重复，是减产品。

**真正的重复是「同一数字有两套名字」**：`report.dynamics.length` 在对比页叫「报告内动态」、
在工作台叫「近期动态」；`quotes.length` 一个叫「收录言论」、另一个叫「经典名言」。两套口径的
结局必然是漂移成两个数字（改一处忘一处），而用户看到的是「同一份报告的两个说法」。

所以：

- **`src/utils/metrics.ts` 是「人 × 指标」行定义的唯一真源**：键、标签、取值、单位、口径说明
  （`hint`）、是否给方向（`higher`）、是否永远显示（`always`）、是否与缓存无关（`ofUncached`）。
- **标签取自章节真源**（`REPORT_TEMPLATE` 的节名）：指标就是「报告里那一段有几条」，报告页改名
  这里跟着改，**不允许手抄第二遍** —— 三个旧名字（报告内动态 / 收录言论 / 履历节点）就此消失。
- **两页各自只声明「显示哪几行」**（`COMPARE_METRIC_KEYS` / `WORKBENCH_METRIC_KEYS`），
  不重排顺序。行集合刻意不同（对比页 = 曝光度 + 素材量；工作台 = 有什么可写 + 生成状态），
  但**交集（热度 / 近期动态）在两页同名同数字**，用例拿同一份报告逐格比对。
- 顺手删掉两个同名不同形状的类型隐患：工作台的 `CompareMetric` → **`CompareTableMetric`**
  （对比页那个是「两人两格」，这个是「N 人 N 格」，同名迟早 import 错一个）。
- 顺手修掉一个**会静默错位**的隐患：工作台先按 `personKey` 过滤脏输入再建行，报告也随之在
  同一条链上取出；此前若回头用 `items[i]` 取报告，中间少一个人就会把数字整体挂到别人名下，
  而错位的表格看起来完全正常（数字都在）。
- 用户可见变化只有三处**变准**：对比页的「报告内动态 / 收录言论 / 履历节点」三个名字对齐成报告里
  的段名；条数带上「条」这个单位（此前同一张表里 `62` 和 `3` 混着摆）；同一指标在两页数字一致。
- 用例 `test/cases/69-metrics.js`（跨模块比对，不是「两处代码长得像」）。**零云侧改动**。

### 埋点登记制落点（2026-10-16）

埋点有一份云侧登记名单（`cloudfunctions/dbInit/schema.js` 里 `events.event` 的 `enumHint`），

  只钉名单不钉顺序 —— 顺序没有语义）。同时钉住「声明了却没有任何 `track(...)` 调用点」：

### 发版前对账工具落点（2026-10-16）

**为什么要有它。** 有一类改动**只在发版那一刻才需要、平时完全无害**，于是必然被忘：

## 七、如果只做三件事

2. **把「变化」变成回来的理由**（N-2 回访）——**已完成（端上待发版）**。

   改了什么」说清楚（N-9），再把它做成回来的理由（N-2）。顺序没反 —— 没有 N-9，
   「有变化」这句话就没有证据。
   ✅ N-2 落地：`history.viewed_generated_at`（我看的是哪一版）× `report_cache.generated_at`
   （现在这一版），**严格晚于**才算变过；**没指纹就不算**（存量行 / 没读出来就退出 = 无证据，

   ✅ 落地：订阅的是**对象**（人 / 关键词），不是单条事件（那是 E1-① 的跟进）—— 两张键空间
   （`subs` 键 = 对象标签，`reads`/`follows` 键 = `event_key`），同一行、同一个写口
   （`saveEventStatus`），**各有各的额度**（订阅不占 `MAX_STATUS_ENTRIES`，否则多读几百条
   事件就把订阅静默挤掉）。消费落点：预警页「订阅的对象」（**先问 `hasSubjectSubs` 再读事件表**，
   没订阅的绝大多数用户不为一张空卡白读两百行）、事件列表页给命中事件打「订阅·X」标。
   ⚠ 待 S0-5 上线后看 `event_subscribe`（`on:true` 的量级）：若订阅关系始终长不起来，
   说明「订阅」这个动作对用户太重（要先进事件详情页才找得到入口），要评估**在报告页也能订阅**
   ——但新增入口前先确认这条链路的消费侧（预警页那张卡）真的被打开过。

> ⚠ 被挤出这条线但**没被否决**的两件事：N-3「条数口径验收」与 S1-5「时刻分布」——
> 都依赖推送（D8）。模板一放开，**N-3 立刻回到第 2 位**（它是所有触达讨论的地基），
> S1-5 排在其后。
