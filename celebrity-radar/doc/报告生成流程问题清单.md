# 报告生成流程 — 问题清单与处置计划

> 建立于 2026-10-17。对象是「点开某个人物 → 拿一份报告」这条链路：从端上闸门到检索、分批生成、
> 达标判定、落库、以及两侧的锁与额度。检查方式是读代码（不是读文档口径），每条都带证据行号。
>
> **这份文档只记录问题与处置，不改任何产品口径。** 处置状态写在每条末尾。

## 一、链路全貌（实际代码路径）

入口只有一个：`src/utils/cache.ts#getOrBuildReport`（`force` 是重生开关）。

| 步 | 做什么 | 位置 |
|---|---|---|
| 1 | 配额闸门：`peekGenerateQuota`（顺带取会员身份 `memberDeep`），通过则记一笔在途占位 | `cache.ts:734`、`799-819` |
| 2 | 查缓存 `getRow` → `isUsable`（`state==='ready' && report`）→ 命中则 `exposeReport` 返回 | `cache.ts:230-232`、`338-347` |
| 3 | 名字回退（`rememberPerson` 记的 altKey）→ 仍未命中则 `acquire` 抢锁，由云端 `aiProxy(action:'report', op:'acquire')` 仲裁 | `cache.ts:415-470` |
| 4 | 抢不到 → `waitForReady` 轮询（2s，上限 `WAIT_TIMEOUT_MS` = 构建上界） | `cache.ts:111`、`590-640` |
| 5 | 检索：`fetchNews` 三层降级（阶梯 → 第二检索源 → `requestChannel` 语义），预算 15s；零素材 → `buildKnowledgeFallback` | `cache.ts:981`、`utils/search.ts` |
| 6 | `buildReport`：按 `REPORT_BATCHES`（4 组）**顺序**调 `chatJSON`，每批 `retries:2` | `report.ts:1820-1830` |
| 7 | `sanitizeReport`：事实字段须有出处、日期归一、会员段保留 | `report.ts:1937` |
| 8 | `shortfallVerdict` 达标判定；不达标且 `retryable` → **整份 4 批再跑一遍** | `report.ts:2640-2683`、`cache.ts:1103-1136` |
| 9 | `saveReady`（云端 `storeSave` 四道校验）→ `consumeGenerateQuota`（`void`，不 await）→ 返回 | `report-store.js:454-486`、`cache.ts:1237` |
| 10 | 异常 / 不达标 → `release` 放锁 → `cachedFallback` | `cache.ts:1148`、`1257` |

数字口径（端上当前值）：单次调用时限 45s、每批最多 3 次、最多 2 遍、4 批、
检索 15s、余量 30s ⇒ 构建上界 **1125s（18 分 45 秒）**，见 `cache.ts:87-101`。

## 二、问题清单

严重度：**高** = 会造成内容作废 / 商业边界失守 / 用户可感的功能失效；**中** = 明显浪费或体验缺陷；
**低** = 技术债、可观测性、口径模糊。

### P1 · 锁超时两端不一致：端上 1125s，云端 405s（高）

- 证据：`cache.ts:95-101`（1125s，随批数 × 尝试数 × 遍数现算）；`cloudfunctions/aiProxy/report-store.js:169-175`（写死 `405 * 1000`，注释自称「**须与端上同值**」）。405s 与「4 批 × 2 次 × 45s + 45s」吻合，是「单批 2 次尝试、无整份重跑」时代的旧值。
- 影响：任何真实耗时 > 405s 的生成（上游抖动触发重试、或触发整份自动重跑）都会被云端判为失联并允许抢占；而 `storeSave` 只认 `builder`（`report-store.js:460`），旧构建者落库被 `kind:'lock'` 拒绝且按约定不回退直写 ⇒ **那一次几十分钟的 token 全废**，用户拿到旧版或失败；第二个人把同样的活再跑一遍。
- 不是理论风险：用户切后台被系统挂起再恢复，正好落进这个窗口。
- 处置（本轮）：两端共用一个真源 —— `src/config/benefits.ts#REPORT_BUILD`（参数集）经 `npm run config:sync` 生成 `cloudfunctions/*/benefits.config.js`，端上 `cache.ts` 与云端 `report-store.js` 用同一组参数各自现算上界。新增用例 `77-build-timeout.js` 钉住「批数 = REPORT_BATCHES.length」「两侧都由真源派生」「云端不许再出现 405」；`08-report-store.js` 里「失联可抢占」的时间点也从真源推导（原来写死「8 分钟前」，是照 405s 估的，上界涨到 1125s 后那条用例会退化成「未失联」）。
- **跟随项**：`quotaGuard#FIRST_BUILD_WINDOW_MS = 20 分钟` 是同一参数的下游派生值（注释里写着 1125s 的算式，用例 48 钉它 ≥ 上界）。改 `REPORT_BUILD` 时必须一起复核，否则首建豁免的时间窗会与新上界失配。
- 状态：**已修（需重新部署 aiProxy；端上随发版）**。

### P2 · `report_cache` 公开可读，会员段只靠端上剥（高）

- 证据：`dbInit/schema.js:22`（`publicReadOnly = {read:true, write:false}`）与 `:149-159`（`report_cache` 用该 ACL）；`report-store.js:371` 注释也这么写。会员段（`memberNotes` / `conflicts` / `peers` / `affiliations`）就存在同一行里，`cache.ts:338-347` 的 `exposeReport` 只是**渲染前** `stripMemberSections`。
- 影响：改包或调试工具直接 `db.collection('report_cache').doc(personKey).get()` 即可拿到会员段全文。付费边界实际只存在于 UI 层 —— 这是「会员权益只剩 2 节」的产品现状之外，更基础的一层漏洞。
- 处置：**待决策，本轮不动代码**。两个方案见第四节。
- 状态：**未修（需产品决策）**。

### P3 · 在途占位 TTL 跟着锁一起放大到 18 分 45 秒（高）

- 证据：`cache.ts:815` 把 `BUILDING_TIMEOUT_MS` 直接当占位 TTL 传给 `quota.ts:144`；`quota.ts:173` 把未过期占位算进 `remaining`；占位的撤销只有两条路（`quota.ts:105-110`）——「计费推进」与「过期」。生成失败/中途退出时 used 不推进，只能等过期。
- 影响：**一次失败就冻结一个名额近 19 分钟**。当天只剩 1 次的用户会被 `allowed=false` 拦住，看到「今日次数已用完」，而 `used` 根本没变 —— 这是用户能直接感知、可复现的 bug，触发条件（生成失败）并不罕见。
- 处置（本轮）：占位 TTL 拆出独立常量 `INFLIGHT_TTL_MS = 180s`，不再与锁同值。理由写在常量注释里：占位只需覆盖「同一个人在一次生成窗口里再点一次」，而锁上界是「构建可能还在正常跑」的悲观值；占位的副作用方向本来就是「宁可少占不可误挡」（`quota.ts:111`）。
- 状态：**已修（随端上发版生效）**。

### P4 · 生成编排在小程序端，切后台即中断（中）

- 证据：整条链路（检索 + 4 批 LLM + 可能整份重跑）都在 `getOrBuildReport` 里跑；锁与占位都靠超时兜底（`cache.ts:83-85`、`quota.ts:109-110`）。
- 影响：锁屏 / 切走 / 网络切换就断在任意一步，token 已花、锁等 405s 才回收、额度冻结直到 P3 修好后的 3 分钟。
- 处置：根治要把生成搬上云（云函数 60s 上限与分批时长冲突，是当初放端上的原因）。**本轮不动**，等 P1 修复后再评估。
- 状态：**未修（结构性）**。

### P5 · 4 批串行，提示词却说「并行」（中）

- 证据：`report.ts:1087` 对本批说「其余分组由**并行的**另几次调用负责」；`report.ts:1820` 实际是 `for ... await` 串行。
- 影响：①措辞与实现不一致（模型可能据此少写）；②串行把总时长乘 4，是 P1 / P3 的放大因素。
- 处置（本轮）：`REPORT_BUILD.batchConcurrency = 4`（`config/benefits.ts`，不手写魔法数），`buildReport` 改为**保序批池**（cursor + 固定 worker，结果按原下标落位），合并与落库仍按批序，故对外行为与串行一致。
  - 与 P8 配套是硬要求：并行把「4 个请求同时撞 429」的窗口放大了，一条 429 ⇒ 该批缺组 ⇒ 必然触发补跑；补跑只发 1 批（P8），不会再把「一次限流」放大成「整份重跑 4 批」。**没有 P8 就不该开这个开关。**
  - 三处必须一起对：①落库（`saveReportParts` 是 building 行 `parts` 的**整字段覆盖**）移到 `settle()`，并用 `partsByKey` 按批序拼快照 + `partChain` 串行化 `onPart` —— 否则并发下后完成的批会用更短的快照盖掉前面的；②进度改用新回调 `onBatchDone`（并发时 `parts.length` 不再等于「已完成批数」）；③`concurrency = 1` 必须保留为完整回退（灰度/回退即改这一个数值）。
  - 刻意**不进 `BUILDING_TIMEOUT_MS`**：云端读不到端上的并发度，失联上界只能是串行口径的悲观值。
- 状态：**已修（随端上发版；灰度 1 → 2 → 4 后观测 429 率）**。

### P6 · `keyword` / `focus` 不进缓存键，命中缓存时静默丢弃（中）

- 证据：`cache.ts:645-657`、`938-943` 明确写「不参与 personKey / 缓存键」。
- 影响：用户输入补充关键词后若命中已有缓存，关键词**完全没参与**生成，页面也不说明。`focus` 有「重新生成以聚焦」提示（选「全部」与选具体侧重命中的是同一行），`keyword` 需核对是否有同等提示。
- 处置（本轮）：不改缓存键（一个词一个键会让共享缓存碎成无数行）。改为**命中缓存且传了 keyword 时提示一句**：`ReportOutcome.keywordUnused` 带回那个词（三处命中路径都带：本 key / altRow / 等来别人构建），报告页渲染一条可关闭的独立提示条（`NoticeKey = 'keywordUnused'`），明说「这次读的是已有报告，关键词只在重新生成时生效」。
- 状态：**已修（随端上发版）**。

### P7 · 会员身份读取失败 → 静默按免费档生成（中）

- 证据：`cache.ts:734` `let memberDeep = false`，只有 `peek` 成功才赋值（`:805`）；`catch`（`:816-819`）只记日志。`lanes` 也按 `memberDeep` 退化（`:942`）。
- 影响：配额服务抖动时，会员拿到「不含会员段、不查社交线」的产物，而页面不会区分「你是免费」与「系统没认出你是会员」。
- 处置（本轮）：`catch` 分支里单独读一次会员状态（`readMemberState`：`memberships` 是权威、一次点查），读到就按会员生成，仍失败则保留降级但把这次「没认出会员」写进 diag 日志。刻意**不复用配额服务的返回值**：能抛错说明那条链路本身可疑，再问一次才是独立证据。
- 状态：**已修（随端上发版）**。

### P8 · 自动重跑是整份 4 批，不是只补失败批（中）

- 证据：`cache.ts:1117` 在 `retryable` 时调用完整的 `buildReport`。而 shortfall 最常见原因是「某一批空导致 facts 不足」（`report.ts:2666`）。
- 影响：为一批失败重烧 4 批，最坏一次生成 24 次 LLM 调用（4 × 3 × 2）。
- 处置（本轮）：`buildReport` 增加 `only`（只跑哪几组）与 `seed`（已有批次结果）。`cache.ts` 首轮在 `onPart` 里留一份**原始字段**的 parts，重跑时按 `missingGroups` 收窄；拿不到明确缺组（例如四批都成功、只是素材少）则退回整份重跑，行为与修复前一致。
- 两处必须一起对：
  ① `seed` 要进 `parts` 的**初值**。`saveReportParts` 写的是 building 行的 `parts` 字段（整字段覆盖，不是按批 upsert），补跑若从空数组开始，已成功的三批会被这一批盖掉；进度播报同理，从种子长度接着数才不会倒退。
  ② 补跑全败时**不许**走 `done === 0` 的纯文本降级。原代码在那里无条件降级，补跑模式下那等于把三批真实素材换成一段「模型已有知识」；现在改为如实返回 `ok:false`，由上层保留首轮残版。
- 效果：「缺一组」的重跑从 4 批 → 1 批（最坏 3 次尝试），最坏总调用 24 → 12。
- 状态：**已修（随端上发版）**。

### P9 · `schemaVersion` 只写不读（低-中）

- 影响：结构升级后旧报告原样渲染，缺字段靠逐字段判空兜。可控，但每次加段落都要再确认一遍兜底。
- 处置：不在本轮。将来若要「按版本决定该不该有这一段」，读口 `reportSchemaVersion` 已就绪。

### P10 · 字段级错误被 `.catch()` 吞掉，只有整批失败才可感知（低-中）

- 证据：`report.ts:1932-1936`（宽容兜底）；`1943` 只在整批失败时落 `missingGroups`。
- 影响：某批返回但个别字段写坏时，那一节静默变空；页面只说「本次确实为空」，不说「解析失败」。两者对用户意义不同。
- 处置（本轮）：把「字段级丢弃」也计入诊断（`missingGroups` 之外加 `report.droppedFields`，并 `diagLog('warn', 'llm', ...)`），页面文案保持现状。实现要点：`pickFields` 在**值存在且过不了严格 schema**（`ZodCatch.unwrap()`）时才记一次丢弃，缺失不记 —— 只有这样才能区分「模型没写」与「写了但写坏」，而且只多一次 `safeParse`，返回给运行时的值与改动前逐字相同（诊断不改解析结果）。
- 状态：**已修（随端上发版，仅诊断）**。

### P11 · 降级纯文本不带素材（低）

### P12 · 检索「没查到」与「没查成」不可区分（低）

## 四、待决策项（P2：会员段的真实边界）

现状：会员段与免费段同住 `report_cache` 一行，读权限是「所有人可读」，端上渲染前剥段。

- **方案 A：会员段拆到独立集合** `report_member`（`_id = personKey`），ACL 改成仅会员可读（云开发安全规则不支持按会员身份判定，实际要「客户端不可读、只有云函数可读」）。
  - 代价：一次数据迁移（存量行拆两行）；读路径从「1 次查询」变「2 次查询」；写口 `storeSave` 要同时维护两行，锁语义不变。
  - 收益：边界落在数据库权限上，改包也拿不到。免费用户读报告不再需要「读完整行再剥」。
- **方案 B：读路径全走云函数**（`op:'get'`），由云函数按 openid 剥段后返回。
  - 代价：每次打开报告多一次云调用（延迟 + 配额），列表页批量读（`getCachedReports`）成本更高；缓存命中这条快路径变慢，与「报告打开要快」冲突。
  - 收益：无需迁移，改包完全无效。
- 倾向：**A**。B 的延迟代价落在最热的路径上，而 A 只在写时多一行、读时多一次点查（会员才读第二行）。

### 4.1 改动量盘点（2026-10-17，只盘点、不下结论）

**先纠正条目里一处低估：漏洞面不止 `report_cache`。** `report_versions` 的 ACL 同样是
`ACL.publicReadOnly`（`dbInit/schema.js:209`），而它存的是**整份旧版 report**（同一份数据里的会员段也在）。
于是「改包直读库」这条路对历史版本同样成立 —— 只堵 `report_cache` 等于只堵一半。两个方案都必须覆盖它。

事实底座（尺寸感来自这里，不是估的）：

### 4.2 决定：走 A，分四阶段（2026-10-17）

结论：**A**。理由不是「B 的工期长」，而是 B 的旧包白屏**没有解法**（小程序不能强制存量升级），
而 A 的最坏情况只是「会员在旧包上看不到会员段」—— 页面自己会显示「这份报告没有会员段落」的补齐引导。
另外阶段 0 已经把「取整份正文的站点」压到 2 处，A 的回归面比盘点时更小。

**关键设计：两份数据不是原子写的，所以配对判据只能是「时间戳逐字相等」。**
`report_cache.generated_at` 与 `report_member.generated_at` 不等时**一律当作没有会员段** ——
宁可少给（会员这一眼看不到四段，页面给补齐引导），也绝不能把上一版的会员段配到这一版的正文上
（那是「用旧结论冒充新结论」，比少给严重得多）。

两条踩过的坑（下次别再试一遍）：

1. **`ModifyDatabaseACL` 不接受 `Rule` 参数**（实测 `UnknownParameter`）⇒ 自定义安全规则 `{"read":false,"write":false}`
   只能进控制台点。所以新表用的是预置档 `ADMINONLY`（「仅管理端可读写」），语义与那条自定义规则完全相同 ——
   回读存量集合会看到 `AclTag: CUSTOM`，不必为了一致去改。口径已写进 `README.md` 的「建集合与权限」。
2. **PowerShell 往 `tcb` 传 JSON 要写成 `'{\"k\":\"v\"}'`**（反斜杠转义的双引号）；`'{"k":"v"}'` 会被剥引号报
   `not a valid JSON string`，`--%` 会被 tcb 当成未知选项。JSON 里**不要带空格**，否则 argv 会被空格拆开。
   `dbInit` 的 `token` 从 `.env` 读进变量拼进去即可，别手抄进命令历史。

**触发判据为什么必须靠旗标**（不看这段，阶段 3 很容易把「补不上」当成偶发）：

「主行没有四段」有两种互斥原因 —— ①这份报告**本来就是免费档生成的**（补也没有）；②主行**被剥了段**（要补）。
端上分不出来。不看旗标就会变成「会员每打开一份免费报告都盲调一次云函数 + 一次限速计数」（几万次/日的白烧）；
反过来只看旗标不看正文，则会在阶段 3 之前（主行仍带四段）白发请求。两个条件都要。

⚠ **阶段 3 的硬契约**：剥段时必须同时写 `report.memberSections = ['memberNotes', …]`（**存在的**那几段字段名）。
漏写 = 端上读口永不触发 = 会员静默看不到四段（不报错、只是少了），只能靠 `member_sections` 埋点的 `empty`
占比被发现。写数组而不是 bool，是因为报告页促销条要能点名「已含对比视角 / 风险提示 / 信源分歧」——
说不出是哪几段就是一句当场兑现不了的承诺。

**阶段 3 之前必须先看的两处**（写在文档里免得那时候重新发现一遍）：

1. `cache.ts#saveReady` 的**端上直写降级分支**仍会把四段写进主行。它现在实际已走不通
   （ACL 已是 `write:false`，只会落到 `degraded`），但阶段 3 要把它与本方案对齐，否则
   「读代码的人会以为还有第二条写入路径」。
2. `hasMemberPayload(row.report)` 有**三处**消费者（`storeSave` 的「只升不降」、`quotaGuard` 的
   免计费复核、`recordVersion` 的取舍）。阶段 3 主行不再有四段时，这三处必须改读副本行，
   漏掉任意一处就会：把会员版判成免费版、让免计费复核永远算「无会员内容」。
3. **非会员的 `locked` 与导出不变式**。「导出必带全量」（S3-1）成立的前提是页面手里的 `report` 已补齐 ——
   阶段 2 之后这条链是通的（`utils/report-export.ts` 只吃页面传入的对象）；顺手查过 `data-export.ts`
   **不读**报告正文，所以不构成第二条路径。真正要改的是报告页促销条：阶段 3 主行不再有四段时
   `presentSections` 返回空 ⇒ `memberLocked` 永远为空 ⇒ 促销条静默消失（只是转化率下降，不报错）。

**阶段 3 已落地的具体内容**（`test/cases/04/08/80/81` 合计新增/改写 20 条）：

- 「这一版是不是会员版」与「正文里还有没有东西要摘」**拆成两个判据**（这是阶段 3 最容易搞混的一处）：
  - `isMemberVersion(report)` = 正文有四段 **或** 带 `memberSections` 旗标 ⇒ 用于「只升不降」与免计费复核；
  - `hasMemberContent(report)` = **只看正文** ⇒ 用于「要不要剥 / 要不要补齐」。
    若让补段判据认旗标，剥段后的报告会恒真 ⇒ `stripMemberSections` 每次白拷一份、`exposeReport`
    每次白读一次身份。
- `aiProxy/report-store.js`：`MEMBER_FLAGS`（token 数组真源，与端上 `utils/member.ts#MEMBER_FLAGS` 逐字相同，
  用例 81 比对）、`memberFlagsOf` / `stripForRow`（**返回新对象**，删四段并写旗标）、`isMemberVersion`；
  `saveMemberRow` 改为**返回布尔**（失败只 `console.warn`）。
- **写库硬顺序：先写副本、成功了才剥主行。** `storeSave` 里
  `const copied = await saveMemberRow(...); if (memberFlags.length > 0 && copied) stored = stripForRow(...)`。
  副本写失败时退回「不剥」—— 宁可主行多带一次四段（方案没生效，但不丢内容），
  也不能出现「旗标说有、副本没有」的静默丢段。用例 08 用**源码顺序断言**钉住这条，用例 80 用行为断言
  （副本写失败 ⇒ `ok:true`、主行四段还在、**不写旗标**）。
- P1-9「只升不降」守卫改判 `isMemberVersion`（旗标也算会员版）：剥段后的行正文没有四段，
  若还只看正文，一次免费重生成就能把会员版覆盖成免费版。
- `quotaGuard#hasMemberBlocks` 末尾补 `Array.isArray(report.memberSections) && length > 0`：
  否则剥段后免计费复核恒判「无会员内容」，可以反复白拿。
- `recordVersion`：只有 `hasMemberPayload(old)` 才搬运历史版副本 —— 旧版本身是剥段形态时，
  `sections` 为空，搬过去等于把已有副本**删行**（`generated_at` 相同、`_id` 相同 ⇒ 覆盖成空壳）。
- `member.ts#presentSections`：正文为空时回退 `sectionsFromFlag(report?.memberSections)`，
  仅三段可进单行促销条（对比视角 / 风险提示 / 信源分歧；冲突与关系是整节，不进促销条）。
  这样剥段后非会员的 `memberLocked` 不会静默变空 ⇒ 促销条不消失。
- `cache.ts#exposeReport`：快路径判据从 `locked.length === 0` 改为 `if (!hasMemberContent(report))`，
  先看旗标 → 再看身份 → 最后补；`saveReady` 的端上直写分支加注释写明**刻意不剥段**
  （端上没有 `report_member` 的写权限，剥了就真丢了）。

**阶段 4 已落地的具体内容**（`test/cases/82-strip-member.js` 14 条）：

- 落点：`dbInit` 新增 `action:'stripMember'`，扫 `report_cache`（`kind:current`）与 `report_versions`
  （`kind:version`，`_id = <personKey>#<生成时间>`），把四段写进 `report_member` 再从主行剥掉。
  **刻意不并进 `sync`**：`sync` 是"每次巡检都能跑"的动作，而这条改的是报告正文。
- 默认 **dry-run**（只回 `candidates` 与 5 个样例 id），`apply:true` 才写，写操作照旧要 `DB_ADMIN_TOKEN`
  （复用 `gateWrites`，没有新增环境变量）。
- 三条硬约束（与写口同一条）：
  1. **先写副本、成功才剥主行**；副本写失败计入 `copy_failed` 并 `continue`，主行原样 —— 下次重跑。
  2. **幂等**：判据是「正文里还有没有四段」，已剥过的行不算候选（重跑 `stripped` 必须为 0）。
  3. **配对键逐字取自这一行**（`report.generatedAt` → 顶层 `generated_at`），算不出来的行
     计入 `without_key` 并**跳过** —— 剥了也取不回来。
- ⚠ **两个踩过的坑，都写进用例了**：
  - `update({ data: { report: {...} } })` **删不掉字段**：平台会把普通对象展开成点号路径再合并
    （`report.memberNotes.compare` 一路展下去）⇒ 迁移报 `stripped=1` 而四段原样还在。必须
    `report: _.set(stripForRow(...))` 整块替换。这就是 2026-10-12 那次线上 P0 的同一条机制。
  - 分批收尾**不能**写 `rows.length < STRIP_PAGE`：一次 `get` 的条数上限跟 SDK 走（客户端 20 /
    服务端 100），请求 100 却只拿到 20 时会在第一页就退出，扫描静默停在 20 条。判据只能是「这一页空了」。
- 分页用 `_id` 升序游标而不是 `skip`：边写边扫时 `skip` 会漏行（用例种 105 行，断言 `scanned=105`）。
- 三处口径（`MEMBER_FIELDS` / 旗标 token）在 `dbInit`、`aiProxy/report-store.js`、端上 `member.ts`
  各有一份 —— 云函数之间不能跨目录 `require`，所以是**手抄副本**，由用例 82 三向逐字比对钉住。

**阶段 4 的跑法**（等阶段 3 部署稳了再执行）：
