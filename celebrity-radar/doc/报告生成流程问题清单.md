# 报告生成流程 — 问题清单与处置计划

> 建立于 2026-10-17。对象是「点开某个人物 → 拿一份报告」这条链路：从端上闸门到检索、分批生成、
> 达标判定、落库、以及两侧的锁与额度。检查方式是读代码（不是读文档口径），每条都带证据行号。
>
> **这份文档只记录问题与处置，不改任何产品口径。** 处置状态写在每条末尾。

## 一、链路全貌（实际代码路径）

入口只有一个：`src/utils/cache.ts#getOrBuildReport`（`force` 是重生开关）。

| 步 | 做什么 | 位置 |
|---|---|---|
| 1 | 配额闸门：`peekGenerateQuota`（顺带取会员身份 `memberDeep`），通过则记一笔在途占位 | `cache.ts:734`、`799-819` |
| 2 | 查缓存 `getRow` → `isUsable`（`state==='ready' && report`）→ 命中则 `exposeReport` 返回 | `cache.ts:230-232`、`338-347` |
| 3 | 名字回退（`rememberPerson` 记的 altKey）→ 仍未命中则 `acquire` 抢锁，由云端 `aiProxy(action:'report', op:'acquire')` 仲裁 | `cache.ts:415-470` |
| 4 | 抢不到 → `waitForReady` 轮询（2s，上限 `WAIT_TIMEOUT_MS` = 构建上界） | `cache.ts:111`、`590-640` |
| 5 | 检索：`fetchNews` 三层降级（阶梯 → 第二检索源 → `requestChannel` 语义），预算 15s；零素材 → `buildKnowledgeFallback` | `cache.ts:981`、`utils/search.ts` |
| 6 | `buildReport`：按 `REPORT_BATCHES`（4 组）**顺序**调 `chatJSON`，每批 `retries:2` | `report.ts:1820-1830` |
| 7 | `sanitizeReport`：事实字段须有出处、日期归一、会员段保留 | `report.ts:1937` |
| 8 | `shortfallVerdict` 达标判定；不达标且 `retryable` → **整份 4 批再跑一遍** | `report.ts:2640-2683`、`cache.ts:1103-1136` |
| 9 | `saveReady`（云端 `storeSave` 四道校验）→ `consumeGenerateQuota`（`void`，不 await）→ 返回 | `report-store.js:454-486`、`cache.ts:1237` |
| 10 | 异常 / 不达标 → `release` 放锁 → `cachedFallback` | `cache.ts:1148`、`1257` |

数字口径（端上当前值）：单次调用时限 45s、每批最多 3 次、最多 2 遍、4 批、
检索 15s、余量 30s ⇒ 构建上界 **1125s（18 分 45 秒）**，见 `cache.ts:87-101`。

## 二、问题清单

严重度：**高** = 会造成内容作废 / 商业边界失守 / 用户可感的功能失效；**中** = 明显浪费或体验缺陷；
**低** = 技术债、可观测性、口径模糊。

### P1 · 锁超时两端不一致：端上 1125s，云端 405s（高）

- 证据：`cache.ts:95-101`（1125s，随批数 × 尝试数 × 遍数现算）；`cloudfunctions/aiProxy/report-store.js:169-175`（写死 `405 * 1000`，注释自称「**须与端上同值**」）。405s 与「4 批 × 2 次 × 45s + 45s」吻合，是「单批 2 次尝试、无整份重跑」时代的旧值。
- 影响：任何真实耗时 > 405s 的生成（上游抖动触发重试、或触发整份自动重跑）都会被云端判为失联并允许抢占；而 `storeSave` 只认 `builder`（`report-store.js:460`），旧构建者落库被 `kind:'lock'` 拒绝且按约定不回退直写 ⇒ **那一次几十分钟的 token 全废**，用户拿到旧版或失败；第二个人把同样的活再跑一遍。
- 不是理论风险：用户切后台被系统挂起再恢复，正好落进这个窗口。
- 处置（本轮）：两端共用一个真源 —— `src/config/benefits.ts#REPORT_BUILD`（参数集）经 `npm run config:sync` 生成 `cloudfunctions/*/benefits.config.js`，端上 `cache.ts` 与云端 `report-store.js` 用同一组参数各自现算上界。新增用例 `77-build-timeout.js` 钉住「批数 = REPORT_BATCHES.length」「两侧都由真源派生」「云端不许再出现 405」；`08-report-store.js` 里「失联可抢占」的时间点也从真源推导（原来写死「8 分钟前」，是照 405s 估的，上界涨到 1125s 后那条用例会退化成「未失联」）。
- **跟随项**：`quotaGuard#FIRST_BUILD_WINDOW_MS = 20 分钟` 是同一参数的下游派生值（注释里写着 1125s 的算式，用例 48 钉它 ≥ 上界）。改 `REPORT_BUILD` 时必须一起复核，否则首建豁免的时间窗会与新上界失配。
- 状态：**已修（需重新部署 aiProxy；端上随发版）**。

### P2 · `report_cache` 公开可读，会员段只靠端上剥（高）

- 证据：`dbInit/schema.js:22`（`publicReadOnly = {read:true, write:false}`）与 `:149-159`（`report_cache` 用该 ACL）；`report-store.js:371` 注释也这么写。会员段（`memberNotes` / `conflicts` / `peers` / `affiliations`）就存在同一行里，`cache.ts:338-347` 的 `exposeReport` 只是**渲染前** `stripMemberSections`。
- 影响：改包或调试工具直接 `db.collection('report_cache').doc(personKey).get()` 即可拿到会员段全文。付费边界实际只存在于 UI 层 —— 这是「会员权益只剩 2 节」的产品现状之外，更基础的一层漏洞。
- 处置：**待决策，本轮不动代码**。两个方案见第四节。
- 状态：**未修（需产品决策）**。

### P3 · 在途占位 TTL 跟着锁一起放大到 18 分 45 秒（高）

- 证据：`cache.ts:815` 把 `BUILDING_TIMEOUT_MS` 直接当占位 TTL 传给 `quota.ts:144`；`quota.ts:173` 把未过期占位算进 `remaining`；占位的撤销只有两条路（`quota.ts:105-110`）——「计费推进」与「过期」。生成失败/中途退出时 used 不推进，只能等过期。
- 影响：**一次失败就冻结一个名额近 19 分钟**。当天只剩 1 次的用户会被 `allowed=false` 拦住，看到「今日次数已用完」，而 `used` 根本没变 —— 这是用户能直接感知、可复现的 bug，触发条件（生成失败）并不罕见。
- 处置（本轮）：占位 TTL 拆出独立常量 `INFLIGHT_TTL_MS = 180s`，不再与锁同值。理由写在常量注释里：占位只需覆盖「同一个人在一次生成窗口里再点一次」，而锁上界是「构建可能还在正常跑」的悲观值；占位的副作用方向本来就是「宁可少占不可误挡」（`quota.ts:111`）。
- 状态：**已修（随端上发版生效）**。

### P4 · 生成编排在小程序端，切后台即中断（中）

- 证据：整条链路（检索 + 4 批 LLM + 可能整份重跑）都在 `getOrBuildReport` 里跑；锁与占位都靠超时兜底（`cache.ts:83-85`、`quota.ts:109-110`）。
- 影响：锁屏 / 切走 / 网络切换就断在任意一步，token 已花、锁等 405s 才回收、额度冻结直到 P3 修好后的 3 分钟。
- 处置：根治要把生成搬上云（云函数 60s 上限与分批时长冲突，是当初放端上的原因）。**本轮不动**，等 P1 修复后再评估。
- 状态：**未修（结构性）**。

### P5 · 4 批串行，提示词却说「并行」（中）

- 证据：`report.ts:1087` 对本批说「其余分组由**并行的**另几次调用负责」；`report.ts:1820` 实际是 `for ... await` 串行。
- 影响：①措辞与实现不一致（模型可能据此少写）；②串行把总时长乘 4，是 P1 / P3 的放大因素。
- 处置：**需先定成本策略**。并行会让 4 个上游请求同时到达，遇厂商限流（`classifyAiError` 429 → `rate`，`RETRYABLE_KINDS` 含 upstream/network）时更容易整批失败，反而触发整份重跑。建议先在灰度开关下试并行 + 保序合并，观测 429 率再全量。
- 状态：**未修（需决策）**。

### P6 · `keyword` / `focus` 不进缓存键，命中缓存时静默丢弃（中）

- 证据：`cache.ts:645-657`、`938-943` 明确写「不参与 personKey / 缓存键」。
- 影响：用户输入补充关键词后若命中已有缓存，关键词**完全没参与**生成，页面也不说明。`focus` 有「重新生成以聚焦」提示（选「全部」与选具体侧重命中的是同一行），`keyword` 需核对是否有同等提示。
- 处置：不改缓存键（一个词一个键会让共享缓存碎成无数行）。改为**命中缓存且传了 keyword 时提示一句**「本次用的是已有报告，关键词需重新生成才生效」。待排期。
- 状态：**未修（待排期）**。

### P7 · 会员身份读取失败 → 静默按免费档生成（中）

- 证据：`cache.ts:734` `let memberDeep = false`，只有 `peek` 成功才赋值（`:805`）；`catch`（`:816-819`）只记日志。`lanes` 也按 `memberDeep` 退化（`:942`）。
- 影响：配额服务抖动时，会员拿到「不含会员段、不查社交线」的产物，而页面不会区分「你是免费」与「系统没认出你是会员」。
- 处置：`catch` 分支里单独读一次会员状态（`readMemberState`），失败才降级；仍失败则保留降级但把 `memberDeep` 的取值来源写进 diag 日志。待排期。
- 状态：**未修（待排期）**。

### P8 · 自动重跑是整份 4 批，不是只补失败批（中）

- 证据：`cache.ts:1117` 在 `retryable` 时调用完整的 `buildReport`。而 shortfall 最常见原因是「某一批空导致 facts 不足」（`report.ts:2666`）。
- 影响：为一批失败重烧 4 批，最坏一次生成 24 次 LLM 调用（4 × 3 × 2）。
- 处置：给 `buildReport` 加「只跑指定批」的入口，按 `missingGroups` 补跑；合并时保留已有 parts。属结构性改动，排下一批。
- 状态：**未修（下一批）**。

### P9 · `schemaVersion` 只写不读（低-中）

- 证据：`cache.ts:230-232`（`isUsable` 只看 state 与 report）、`:258-273`（注释明说「现在不因版本低而丢弃缓存」）。
- 影响：结构升级后旧报告原样渲染，缺字段靠逐字段判空兜。可控，但每次加段落都要再确认一遍兜底。
- 处置：不在本轮。将来若要「按版本决定该不该有这一段」，读口 `reportSchemaVersion` 已就绪。
- 状态：**未修（技术债）**。

### P10 · 字段级错误被 `.catch()` 吞掉，只有整批失败才可感知（低-中）

- 证据：`report.ts:1932-1936`（宽容兜底）；`1943` 只在整批失败时落 `missingGroups`。
- 影响：某批返回但个别字段写坏时，那一节静默变空；页面只说「本次确实为空」，不说「解析失败」。两者对用户意义不同。
- 处置：把「字段级丢弃」也计入诊断（`missingGroups` 之外加 `droppedFields`），页面文案保持现状。待排期。
- 状态：**未修**。

### P11 · 降级纯文本不带素材（低）

- 证据：`report.ts:1905` 只传 `名人：{name}`；`shortfallVerdict`（`report.ts:2653`）把它判为不达标且不落库。
- 影响：产物是模型既有知识、无出处。好在有 `degraded` 标记且不落缓存，风险被收住；但与「事实只基于素材」的原则有张力。
- 处置：本轮不动（已有标记 + 不落库 + 页面提示三重约束）。

### P12 · 检索「没查到」与「没查成」不可区分（低）

- 证据：第二检索源失败静默降级；`requestChannel` 的 null / [] / 抛错三态只在诊断日志里（`utils/search.ts`）。
- 影响：境外默认关闭第二源时，报告说「未检索到素材」，真相是「没查成」。用户会以为这个人没新闻。
- 处置：`knowledgeOnly` 的文案里补一句「（检索通道未就绪时会这样）」。待排期。

### P13 · 无自动过期 / 预热（低）

- 证据：`cache.ts:227-228` 明确「不设时间上限、不做自动过期重生」。
- 影响：冷门人物可能长期是几个月前的报告，页面只有一句「N 天前生成」。
- 处置：不在本轮（涉及定时任务与成本）。

## 四、待决策项（P2：会员段的真实边界）

现状：会员段与免费段同住 `report_cache` 一行，读权限是「所有人可读」，端上渲染前剥段。

- **方案 A：会员段拆到独立集合** `report_member`（`_id = personKey`），ACL 改成仅会员可读（云开发安全规则不支持按会员身份判定，实际要「客户端不可读、只有云函数可读」）。
  - 代价：一次数据迁移（存量行拆两行）；读路径从「1 次查询」变「2 次查询」；写口 `storeSave` 要同时维护两行，锁语义不变。
  - 收益：边界落在数据库权限上，改包也拿不到。免费用户读报告不再需要「读完整行再剥」。
- **方案 B：读路径全走云函数**（`op:'get'`），由云函数按 openid 剥段后返回。
  - 代价：每次打开报告多一次云调用（延迟 + 配额），列表页批量读（`getCachedReports`）成本更高；缓存命中这条快路径变慢，与「报告打开要快」冲突。
  - 收益：无需迁移，改包完全无效。
- 倾向：**A**。B 的延迟代价落在最热的路径上，而 A 只在写时多一行、读时多一次点查（会员才读第二行）。

在决策前，`report_cache` 的 ACL 保持现状（收紧写权限已经完成，读权限的收紧依赖上面的选择）。
