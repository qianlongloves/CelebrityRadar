## 一、先读：五条前提（决定后面所有取舍）

1. **集合必须先建**。客户端往不存在的集合 `add` 会报 `-502005 database collection not exists`，
   且 `select` 也可能直接报错，表现为「登录初始化失败」。
2. **主键固定是 `_id`**。端上代码统一按业务字段 `id` 书写，由 `src/utils/db.ts` 适配层做
   `id ↔ _id` 双向映射（见该文件头注释）。**除 `users` 外，各集合的 `_id` 由端上显式指定**
   （形如 `openid#personKey`）⇒ 天然防重，**不需要额外唯一索引**。
3. **`_openid` 由云端在客户端 `add` 时自动注入**（登录用户）。它是权限判定与「仅创建者可读写」的依据；
   对 `users` 集合而言，它还是**端上唯一能取得自己身份**的途径（云开发不提供客户端换 openid 的 API）。
4. **小程序端单次查询上限 20 条**。`db.ts` 已内部分页续取（`fetchAll`），但高频过滤字段仍**必须建索引**，
   否则深分页会逐页变慢。
5. **云函数不受集合权限限制**：`aiProxy` / `notifyFollowUpdates` / `quotaGuard` / `hotBoardRefresh` 以管理员身份读写，
   故 `notifyFollowUpdates` 能在「仅创建者可读写」的 `users` / `follows` 上做全表扫描，
   `quotaGuard` 能在 `write: false` 的配额表上写入（这正是 §四 收紧配额表权限的前提），
   `hotBoardRefresh` 也能在 `write: false` 的 `hot_board` 上覆盖写 `latest`。

> ⚠ **两条与旧 SQL 版的硬差异（旧版有错，以此为准）**
> - `users` **没有 `id` 字段**，主键是云端生成的 `_id`（`auth.ts` 的 `insert` 不带 `id`）。
>   旧 SQL 写的「`id = 'wx:' + openid`」是**错的**，按它建库会导致端上读不到自己的行。
> - `favorites.type` 有**四个**取值：`quote | report | dynamic | timeline`（见 `utils/favorites.ts` 的
>   `FavoriteType`）。旧 SQL 的 `check (type in ('quote','report'))` 会让「收藏动态 / 时间线」写入失败。

### 5. `generate_quota` —— `src/utils/quota.ts` + 云函数 `quotaGuard`
| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 云端 | `${openid}#yyyy-MM-dd` |
| `_openid` | string | 云端 | 同上 |

> 三张配额表均已**服务端化**：`count` 由云函数 `quotaGuard` 原子自增（`db.command.inc(1)`），日期取服务端时间（防改设备时间绕过）。
> **2026-10-07 状态**：`quotaGuard` 已部署，但**部署的是不含 `ask` 类的版本** —— `ask_quota` 要先按 §六 建表、
> 再重新部署 `quotaGuard`（新白名单才认 `ask`），之后才能按 §四 把三张表一并收紧为「本人可读、不可写」。
> 收紧前先确认端上确实走的是服务端计数：生成一次报告后看 `generate_quota` 是否出现 `openid#当天` 行、
> 问一次 AI 后看 `ask_quota` 是否有行；若仍是端上回退计数（诊断日志会打「quotaGuard 未部署，…暂用端上计数」），先别收紧。
> 云函数未部署时端上静默回退读-改-写（`utils/quota-guard.ts`）—— 此时可超发、可被改时间绕过，属**过渡态**，
> 部署函数 + 收紧权限（§四）后消失。

> 三张表是**三套独立额度、勿混用**：刷新 10（`refresh_quota`）/ 生成 免费 3 · 会员 30（`generate_quota`）/
> 提问 免费 5 · 会员 30（`ask_quota`）。

### 12. `ask_quota` —— `src/utils/qa.ts` + 云函数 `quotaGuard`
| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 云端 | `${openid}#yyyy-MM-dd` |
| `_openid` | string | 云端 | 同上 |
| `count` | number(int) | 云端 | 当日**成功回答**次数（被额度拦 / 机审命中 / 无素材 / 模型报错都不计） |

> 编号续在 §二 末尾（配额族第三张，字段与第 4 / 5 节完全同构），不插进 4 / 5 之间是为了避免全文重编号。
> ⚠ 与另两张有一条**语义差异**：生成 / 刷新是「**发起时**自增」，提问是「**拿到回答才**自增」——
> 端上先读本行判额度、成功后（`utils/qa.ts#noteQaUsed`）才调 `quotaGuard` 的 `ask` 类。
> 故并发下可能多问一两次，可接受（有 3 秒连点间隔，且额度本身够宽）。
>
> ⚠ **顺序坑（比另两张更刁）**：若「表已建 + 权限已收紧 + 但 `quotaGuard` 还是旧版本」，
> 自增一律失败 ⇒ 表里永远没有行 ⇒ 端上把「读不到行」当 0 ⇒ **额度形同虚设**。
> 端上对此有防御（`utils/qa.ts#raiseMirror`：镜像只抬高、不覆盖，判定取两端较大值），
> 所以额度不会被漏掉，但会出现「云端 0、本机说已用 N 次」的读数不一致 —— 看到就该去重部署函数。

### 6. `follows` —— `src/utils/follows.ts`
| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 端上 | `${userId}#${personKey}` |
| `openid` | string | 是 | 业务字段，= `${userId}` |
| `person_key` | string | 是 | `名字#领域码`（含 `#`，**禁止 split 反解析**，走 `parsePersonKey`） |

**`report_cache` / `feed_cache` 的自定义安全规则**（语义：所有人可读，已登录可写）：

```json
{
  "read": true,
  "write": "auth.openid != null"
}
```

> - `read: true` 覆盖未登录读取（共享缓存必须）。
> - `write` 只要求「已登录」，**不能**写成 `doc._openid == auth.openid` —— 那会把跨用户抢占与刷新重新锁死。
> - 这两张表是**可再生的公共数据**，放宽写权限的风险面仅限于「缓存被篡改/清空」，可接受；
>   真正不可信的个人数据（`follows` / `favorites` / `history` / `*_quota` / `users`）一律收紧到创建者。
> - 若控制台语法提示与本 JSON 不一致，以其提示为准（微信用的是受限表达式语言）。

**`refresh_quota` / `generate_quota` / `ask_quota` / `orders` 的自定义安全规则**（语义：仅本人可读，任何人都不可写）：

```json
{
  "read": "doc._openid == auth.openid",
  "write": false
}
```

> - `write: false` 就是这几张表服务端化的**全部意义**：写入只允许对应云函数（`quotaGuard` / `payCreate` / `payCallback`，管理员身份，不受安全规则约束）。
> - ⚠ **`quotaGuard` 这两步的顺序不可颠倒**：**先部署函数并确认生效，再设这条规则**。
>   若先设规则而函数尚未部署，端上回退写入会被拒绝 ⇒ `count` 恒为 0 ⇒ 免费额度形同虚设。
> - `orders` 无顺序依赖：端上从不写订单（没有回退逻辑），权限可随时收紧。
> - `read` 不能写成 `false`：端上仍要读自己那行（生成前闸门检查 / 「我的」页配额卡 / 订单排查）。
> - 部署方式见 §十一 路径 A；过渡态与回退逻辑见 `src/utils/quota-guard.ts`。
> - **不必手抄上面那段 JSON**：云函数 `dbInit` 的 `{"action":"report"}` 会在 `permissions_manual[]` 里给出
>   每张表的 `rule`（对象）与 `rule_json`（**可直接粘进控制台**的单行串），`acl` 字段写明属于哪种口径。
>   2026-10-18 起才带这两个字段（此前只给一句「见 README」，等于把唯一能照着做的东西留在了别处）。

**`keywords` / `risk_scans` / `risk_signals` / `opinion_events` / `person_assets` 的自定义安全规则**（语义：所有人可读，端上任何人都不可写）：

```json
{
  "read": true,
  "write": false
}
```

> - 这五张表**只由云函数**（`keywordAlert` / `riskWatch` / `opinionCluster` / `aiProxy`）以管理员身份写，端上**从不写** ⇒ 写权限收到最紧。
> - `read` 必须放开（含未登录）：预警页要看的是「搜出来的结果 / 扫出来的信号」这类**公共事实**，
>   不是某个用户的数据；收紧成 `doc._openid == auth.openid` 会让预警页永远空白
>   —— 函数建的行的 `_openid` 归属管理员，端上读不到（与 `hot_board` 同一个坑）。
> - `keyword_watches` **不适用**这条规则：它的行是端上建的，必须保持「仅创建者可读写」。

**`hot_board` 的自定义安全规则**（语义：所有人可读，**任何人**都不可写）：

```json
{
  "read": true,
  "write": false
}
```

> - `read` 必须是 `true` 而不是 `"auth.openid != null"`：首页是 tabBar 页，**未登录也要能看榜**
>   （榜单不含任何个人信息），用登录态去卡它只会让首屏运营位空着。
> - `write: false` 与 `report_cache` / `feed_cache` 的 `"auth.openid != null"` **刻意不同**：
>   那两张表是「端上要抢锁 / 跨用户写」的共享缓存，而 `hot_board` 的写方**只有云函数** ——
>   云函数是管理员身份，**不受安全规则约束**，所以收紧到 `false` 不会影响 `hotBoardRefresh` 落库。
> - ⚠ 顺序无关（与 `quotaGuard` 那两张不同）：端上**从不写** `hot_board`，没有「回退写入」这回事，
>   所以先设权限还是先部署函数都不影响功能；真出问题只会表现为榜单为空 + 端上自触发一轮补跑。
> - 这与 `cloudfunctions/dbInit/schema.js` 里的 `ACL.publicReadOnly` 是**同一份定义的两处落点**；
>   权限**无法程序化**（`dbInit` 的巡检会把它列进清单，但设置必须手工，见 §六）。

**`memberships` / `ai_calls` / `deep_dive_quota` 的自定义安全规则**（语义：客户端**连读都读不到**）：

```json
{
  "read": false,
  "write": false
}
```

> - 这三张是**服务端权威 / 服务端约束**：`memberships` 是会员权益的判据，`ai_calls` 与 `deep_dive_quota`
>   是滥用与成本的边界。**端上碰不到它们不是缺陷，而是设计前提** —— 端上要显示的会员档位读的是
>   `users.membership`（可读镜像，由 `payCallback` 双写；端上读口 `utils/member.ts#readMemberState`）。
> - `read: false` 会让端上的 select **直接失败**，所以**别把「端上读不到」当配置错误去排查**：
>   端上本就不读这两张计数表。
> - 与 `cloudfunctions/dbInit/schema.js` 的 `ACL.cloudOnly` 是同一份定义的两处落点；权限无法程序化，必须手工设。

## 六、建集合的方式

> **当前状态（2026-10-14 校正）**：集合清单以 `dbInit/schema.js` 为准，共 **22 张**（§二）。
> 本文档**不再逐张记录「控制台建齐到第几张」** —— 那种「进度记录」正是它两次过期的方式（最近一次停在 16 张）。
> **先跑 `dbInit` 的 `{"action":"report"}`（方式 B）拿到体检结果**（集合 / 字段 / 索引一次列全，权限另列清单），
> 缺哪张按 §二 补哪张；**权限无法程序化**，必须手工。
> ⚠ **建表 ≠ 可用**，两张最容易漏的：① `keyword_watches` 权限没设成「仅创建者可读写」时，
> 「+ 监控风险」与关键词订阅必然失败；② `memberships` / `ai_calls` / `deep_dive_quota` 若被设成可读，
> 等于把会员判据与成本闸门交给改包者（§四）。
> 本节其余内容为步骤留档（换环境 / 重建 / 新增集合时用）。
> 仓库现有**运维工具 `cloudfunctions/dbInit/`**（比旧的 `initDb` 多出**字段比对**与**索引建改**两件事）：
> 它能把 §五 的索引一键建齐 —— 见方式 B。

### 方式 A（控制台手动新建集合）：与方式 B 二选一

1. 微信开发者工具 → 云开发 → 数据库 → 「+」→ 输入集合名（§二 表格第一列，**区分大小写、勿用中文**）。
2. 集合名逐张抄 §二 表格（共 22 张），**先核对、缺则补**；日后新增集合时重复此步。
   （本文档原先在这里写着「前 12 个已建齐、后 4 个待补」—— 这种进度记录必然过期，故删掉，一律跑体检核对。）
3. 逐个设权限（§四）与索引（§五）。
4. 字段**无需手动定义**（文档型数据库无 schema），首次写入自动带上。

### 方式 B（当前首选）：运维云函数 `dbInit` 一键建集合 / 比字段 / 建索引

环境重建（换 envId、开测试环境、集合被误删）、补集合、字段与索引演进，都用仓库里的
**`cloudfunctions/dbInit/`**：它是**常驻仓库的运维工具**，端上任何代码都不调用它。
「是什么」全在 `cloudfunctions/dbInit/schema.js`（与本文档一一对应，改字段只改它 + 本文档）。

```bash
# 1) 部署（首次，或改了 schema.js 之后）
tcb login                                                 # 一次性
tcb fn deploy dbInit -e <your-env-id>
```

> CLI 的通用说明（为何用 CLI 而非开发者工具、环境变量占位符、参数以 `-h` 为准）见 §十一 路径 A。

```jsonc
// 2) 先巡检（dry-run，只读不改）—— 控制台 → 云函数 → dbInit → 「测试」传入：
{ "action": "report" }
// 或 CLI：tcb fn invoke dbInit --params '{"action":"report"}'
// 输出：每张集合是否存在 + 字段差异（缺失 / 多余 / 类型不符 / 必填缺失告警）
//       + 索引计划 + 权限人工核对清单
```

```jsonc
// 3) 写操作（须先给 dbInit 配环境变量 DB_ADMIN_TOKEN，并带上同一口令）
{ "action": "init",    "apply": true, "token": "<口令>" }                        // 建缺失的集合（补 orders 用这个）
{ "action": "fields",  "apply": true, "token": "<口令>" }                        // 按 schema.js 的 def 补齐可选字段
{ "action": "indexes", "apply": true, "token": "<口令>" }                        // 建索引（需 WX_APPID / WX_APPSECRET）
{ "action": "indexes", "apply": true, "token": "<口令>", "rebuild": true }       // 定义变了：先 drop 后 create
{ "action": "sync",    "apply": true, "token": "<口令>" }                        // = init + fields + indexes
```

要点（与 §一 五条前提一脉相承）：

- **默认 dry-run**：`action` 缺省 `report`；任何写路径都要显式 `apply: true`，`report` 永远只读。
- **口令闸门**：`dbInit` 以管理员身份运行、能读写任何集合，而云函数只要部署就能被小程序端调到 ⇒
  没配 `DB_ADMIN_TOKEN` 时**写操作一律拒绝**（只读巡检不限）。
- **口令强度与轮换**（2026-10-22 起统一）：`DB_ADMIN_TOKEN` / `PAY_ADMIN_TOKEN` / `AI_PROXY_TEST_TOKEN` 守的都是
  「能改数据」或「真花钱」的门（dbInit 能读写任意集合、payCallback 的运营写口能改会员与退款、aiProxy 的 `test`
  每调一次就打一次博查 + 大模型），**未配置即拒绝**，所以口令本身就是全部强度 —— 用 32 字节随机串、
  三枚互不相同（`openssl rand -hex 32`，PowerShell 见 `.env.example`）。值只写在 `.env`（已被 `.gitignore` 的
  `.env*` 挡住），`cloudbaserc.json` 里是 `{{env.*}}` 引用 ⇒ **改口令必须 `tcb fn deploy` 重部署对应函数，
  `tcb fn code update` 不会更新环境变量**；`PAY_ADMIN_TOKEN` 还被 `payCallback` / `adminOps` / `adminConsole`
  三者逐字比对，**必须同批换**。控制台「云端测试」里存过的调用参数要同步替换（旧口令立即失效）。
- **`only` 限定范围**：`"only": ["orders"]` 只处理 `orders`；不在 `schema.js` 声明的 16 张表白名单里的名字直接拒
  （表名永不来自调用方，避免被当跳板遍历任意集合）。
- **字段只补「可选字段」**：`schema.js` 里带 `def` 的按默认值补齐（幂等的 ADD COLUMN DEFAULT）；
  `required: true` 的缺失**只报告、不回填** —— 那说明数据本身有问题，拿默认值盖住会让问题永远查不出来。
- **索引靠 HTTP API**：`wx-server-sdk` 没有索引 API，故走下面的「更新索引」接口，需 `WX_APPID` / `WX_APPSECRET`
  （或直接传 `access_token`）；没配凭据就只输出**可复制的请求体**供手工建。
- **用完可删**：`tcb fn delete dbInit`。下次要用再从仓库部署 —— 这也是它留在仓库、
  而不像旧 `initDb` 那样被移除的原因：字段与索引会随版本演进，重建环境是常态。

> ⚠ **部署时必须选「上传并部署：云端安装依赖」**。微信云函数运行时**不再预置** `wx-server-sdk`：
> 「上传并部署：所有文件」只打包本地目录，本地没有 `node_modules` 时会报
> `Error: Cannot find module 'wx-server-sdk'`（require stack 指向 `/var/user/index.js`）。
> 三个选项里只有「云端安装依赖」会按 `package.json` 在云端执行 `npm install`。

> ⚠ **索引与权限要分开看**（2026-10-07 校正，旧稿写「都管不到」不准确）：
> - **索引可以程序化**：`wx-server-sdk` 确实没有索引 API，但微信云开发 HTTP API 有
>   「[更新索引](https://developers.weixin.qq.com/doc/oplatform/Third-party_Platforms/2.0/api/cloudbase/common/updateindexinfo.html)」
>   —— `POST https://api.weixin.qq.com/tcb/updateindex?access_token=…`，body 为
>   `{ env, collection_name, create_indexes: [{ name, unique, keys: [{ name, direction }] }], drop_indexes: [{ name }] }`。
>   **但该接口只有「按索引名新增 / 删除」，没有「列出已有索引」** ⇒ `dbInit` 的做法是
>   **按钉死的索引名幂等 create**（报「已存在」即视为在位）；定义变了则 `rebuild: true` 走「先 drop 后 create」，
>   这就是「**更新**索引」的全部含义。索引名见 `cloudfunctions/dbInit/schema.js`，**改名等于留孤儿索引**。
> - **权限仍然管不到**：没有任何接口能改集合权限，必须按 §四 在控制台设置。
>
> 漏建索引不报错、只在深分页时变慢；漏设权限则直接是**安全与功能问题**（见 §四 各行的「理由」列）。

> 想省事：先跑 `dbInit` 的 `{ "action": "report" }`，一次拿到「集合有无 / 字段差异 / 索引计划」体检报告
> （它连带日期的字段类型不符都会点名，见 §六 方式 B）。下面这段 Console 脚本用于**端上视角**的核对 ——
> 走的是用户身份与权限，能顺带验证 §四 的权限是否真的配对了，这是管理员身份的 `dbInit` 验不出来的。

在微信开发者工具 Console 逐段执行（需已填 `public.ts` 的环境 ID 并重新编译）：

```js
const db = wx.cloud.database()

// 1) 22 个集合是否都在（预期 22 行，缺哪个补哪个）
const names = ['users','report_cache','feed_cache','refresh_quota','generate_quota',
               'follows','favorites','history','events','orders','hot_board','ask_quota',
               'keyword_watches','keywords','risk_scans','risk_signals',
               'memberships','ai_calls','deep_dive_quota',
               'opinion_events','opinion_event_status','person_assets']
for (const n of names) {
  try { await db.collection(n).limit(1).get(); console.log('[ok]', n) }
  catch (e) { console.warn('[missing]', n, e.errMsg || e.message) }
}
//    ⚠ 这一步只证明「集合存在且**可读**」。`keyword_watches` 还得能**写**（权限「仅创建者可读写」）：
//      在报告页点一次「+ 监控风险」验证 —— 写不进去时端上会弹窗点名是集合没建还是权限不对。

// 2) users 权限是否为「仅创建者可读写」：登录后应只取到本人这一行
const me = await db.collection('users').get()
console.log('users rows =', me.data.length, '（预期 1；若 >1 说明权限过松或曾并发重复插入）')
console.log('my _openid =', me.data[0] && me.data[0]._openid)

// 3) hot_board 权限与内容：未登录也应能读到 latest 这一行（读不到 = 权限没设对，端上会静默退回静态池）
const board = await db.collection('hot_board').doc('latest').get().catch((e) => e)
console.log('hot_board =', board && board.data ? `${board.data.items?.length} 位 / ${board.data.date}` : (board.errMsg || board.message))
```

| `hotBoardRefresh` | **定时器** `dailyHotBoard` 每天 06:30<br>+ 端上 `ensure` 冷启动补跑 | `utils/hot-board` | **60s** | `BOCHA_API_KEY`<br>`DEEPSEEK_API_KEY` |
| `dbInit` | **人工运维调用**（端上不调用） | 无 | 60s | `DB_ADMIN_TOKEN`<br>`WX_APPID` / `WX_APPSECRET` |
| `adminOps` | **控制台 / CLI**（`callerGuard` 明确拒绝带 OPENID 的调用） | 无 | 60s | `ADMIN_OPS_TOKEN`<br>`PAY_ADMIN_TOKEN` |
| `adminConsole` | **端上云调用（仅超管）**——openid 白名单 `ADMIN_OPENIDS`，未配置即全部拒绝 | `utils/admin.ts` → `package/admin` 运维中心 | 20s | `ADMIN_OPENIDS`<br>`PAY_ADMIN_TOKEN` |
| `opsCheck` | **定时器** `dailyOpsCheck` 每天 10:30<br>+ 手动带 `token` 跑一次（只读） | 无 | 60s | `OPS_WEBHOOK_URL`<br>`DB_ADMIN_TOKEN` |

> **三个推送函数为什么要 `WX_APPID` / `WX_APPSECRET`**：它们由**定时器**触发，而微信云调用的
> 「免鉴权」只在**由小程序端触发的云函数**里成立（CloudBase 错误码 `INVALID_WX_ACCESS_TOKEN` 的官方
> 解释就是「未从小程序端触发使用云调用的云函数」）。所以三个函数的发送统一走 `sendSubscribeMessage`：
> 先试 `cloud.openapi.subscribeMessage.send`（将来若改成端上触发、或平台行为变化，它仍是最省事的一条），
> 只有「通道类」错误（`invalid wx openapi access_token` / `openapi permission denied` / `-501001` 等）
> 才降级到自取 `stable_token` 直连 `/cgi-bin/message/subscribe/send`。
> **2026-10-22 实测**：同一枚模板、同一个 openid，自取 token 直连返回 `errcode:0` 并真实收到消息，
> 而云调用同一时刻报 `invalid wx openapi access_token` —— 即「模板/参数/授权都对，卡的只是定时器这条
> 调用链拿不到自动鉴权」。⚠ 43101（用户没授权）**不在**降级判据里：那属正常业务状态，重试只会白耗一次
> 发送机会，还会把「用户取消授权」伪装成基础设施故障。
>
> `adminOps` 与 `adminConsole` 刻意不合并：前者是「有口令、没有 openid」，后者是「有 openid、没有口令」，
> 两套闸门语义相反；混在一起时任何一侧的疏漏都会变成另一侧的突破口。
> `adminConsole` 的会员写操作**不直接落库**，一律代理 `payCallback`（会员数据仍只有一个写口）。

> 60 秒的几条（`aiProxy` / `hotBoardRefresh` / 三个推送函数）是最容易出事的：微信云开发默认 20 秒，被掐断后端上只能拿到 `-504003`，函数里的错误结构化信息一个都传不回来（见 `utils/cloud.ts#cloudTimeoutHint`）。

### 三枚订阅模板 ⇄ 三个推送函数（2026-10-22 现状）

一次性订阅**按模板消耗授权**：同一枚 `templateId` 被两个定时任务共用，就是「09:00 先跑的吃掉授权，09:20 后跑的必得 43101」。所以三路必须各用一枚不同的模板，`cloudbaserc.json` 也按函数逐个注入，不共用。

| `.env` 变量 | 注入函数 | 实际选到的模板 | 用户看到的固定文案 | 评价 |
|---|---|---|---|---|
| `SUBSCRIBE_TEMPLATE_ID` | `notifyFollowUpdates` | 订阅文章更新通知 | `标题：` / `发布日期：` | 贴合 |
| `ALERT_TEMPLATE_ID` | `keywordAlert` | 预订提醒 | `预订内容：` / `预订时间：` | 将就（内容是「预订的内容」勉强成立） |
| `RISK_TEMPLATE_ID` | `riskWatch` | 未读日报提醒 | `录入人：` / `日期：` | **最别扭**（`录入人：张三出现司法监管类表述…`） |

两件事要分清：

- **换模板不改代码**：拿到语义更贴的模板后，只改 `.env` 里对应那一行，再 `tcb fn deploy <函数> --force`（或 `tcb fn code update`）。只有新模板的时间键**不叫 `time2`** 时，才需要动 `data` 的键名与格式器。
- **固定文案由模板锁死**：`thing1` 只填值，前缀 `录入人：` 是模板自身的提示语，代码无法覆盖或隐藏。所以「文案不对」只能靠换模板解决，不能靠调文案。
- 未开通/未选模板时**留空该变量**：对应函数启动会直接 `skipped: '缺少环境变量：XXX_TEMPLATE_ID'`，不会误发、也不影响另外两路。
- **文案与通道是两件事**：模板决定「消息里那几个字的标签」，通道决定「消息发不发得出去」。2026-10-22 之前三个定时任务卡在通道上（云调用在定时器里拿不到鉴权），文案再怎么换也收不到；现在发送走 `sendSubscribeMessage` 的双通道（见 §五 调度表下），换模板只影响观感，不再影响可达性。

## 十一、路径 A：部署后真实执行

### A-1 CloudBase CLI（推荐）

```powershell
npm i -g @cloudbase/cli      # 本机尚未安装 tcb
tcb login
cd c:/workspace/celebrity-radar/celebrity-radar   # cloudbaserc.json 在这一层
tcb fn deploy quotaGuard -e <your-env-id>
```

CLI 相对开发者工具的三个优势（都在 `cloudbaserc.json` 里）：

| 项 | CLI 行为 |
|---|---|
| `timeout` | 随云 API 下发，**无需控制台手改** |
| `triggers` | 定时触发器一并建立 / 更新 |
| `installDependency: true` | 依赖在云端安装，本机不用 `npm install`（云函数目录下确实没有 `node_modules`） |

⚠ 两条必须记住的：

1. **环境变量占位符**：`cloudbaserc.json` 里写的是 `"BOCHA_API_KEY": "${env.BOCHA_API_KEY}"`，取值来自**本机 shell 环境变量**。部署前先确认：
   ```powershell
   $env:BOCHA_API_KEY; $env:DEEPSEEK_API_KEY     # 无输出 = 会被传成空串
   ```
   传成空串后函数不会报错，只会回 `{ ok:false, kind:'unconfigured' }`，端上表现为「平台大模型通道未就绪」。
2. **部署顺序红线（颠倒会静默放宽额度）**：
   ① 先 `tcb fn deploy quotaGuard` → ② 真机打开任一带报告的页面，确认配额数字正常（不是恒 0）→ ③ **再**把 `generate_quota` / `refresh_quota` / `ask_quota` 三张表权限收紧为「本人可读、不可写」（§四）。
   反过来做：端上回退写入被权限拒绝、计数恒 0 ⇒ 免费额度形同虚设。

> 命令参数名以 `tcb fn deploy -h` / `tcb fn invoke -h` 为准（CLI 各版本略有差异）。

### A-2 微信开发者工具「上传并部署」

只在这几处与 CLI 不同：

| 项 | 开发者工具 |
|---|---|
| `cloudbaserc.json` | **完全不读** |
| 超时时间 | 回控制台手改：云函数 → `aiProxy` → 配置 → 超时时间 **60 秒**（默认 20） |
| 环境变量 | 回控制台手填 |
| 触发器 | 回控制台 → 触发器 → 新建（Cron **7 段**：`0 30 6 * * * *`） |
| 函数目录内 `config.json` | **只有 `permissions.openapi` 会生效**，其中的 `timeout` 只对 CLI 有效 |
| 依赖安装 | 必须选「上传并部署：**云端安装依赖**」，否则报 `Cannot find module 'wx-server-sdk'`（见 §六 方式 B 末） |

### A-3 必须部署 vs 可以不部署

这套代码对云函数做了完整的降级设计，所以「没部署」不等于「坏了」：

| 函数 | 不部署时端上表现 |
|---|---|
| `aiProxy` | 生成链路直接报「云函数 aiProxy 未部署」（唯一通道，无备选）；检索返回 null → 读共享缓存 → 引导态 |
| `quotaGuard` | **静默**回退本机计数（额度仍生效，但可被改包绕过） |
| `contentCheck` | fail-open 放过（用户输入仍可提交，只是没有机审兜底） |
| `hotBoardRefresh` | 热门榜退回「真实热度 → 静态种子」两档 |
| `payCreate` / `payCallback` | 「我的」页提示「支付服务未部署」，不影响免费功能 |
| `notifyFollowUpdates` | 无订阅推送，不影响其它功能 |
| `dbInit` | 端上零调用，可完全不部署 |

**结论**：只有 `aiProxy` 是硬依赖，`quotaGuard` 是「该部署」（不部署就用不了服务端权威计数），其余按需。

## 十五、报错速查

| 现象 | 成因 | 处理 |
|---|---|---|
| 端上 `-504003` / `Invoking task timed out` | 函数超时被平台杀（默认 20s） | 把 `aiProxy` / `hotBoardRefresh` / `notifyFollowUpdates` 超时改 60s |
| 「云函数 aiProxy 未部署」/ `-501000` | 函数没部署或云环境 ID 不对 | 部署 `aiProxy`；核对 `public.ts#cloudbaseEnvId` |
| 「平台大模型通道未就绪」/ `kind:'unconfigured'` | 函数部署了但环境变量为空 | 补 `BOCHA_API_KEY` / `DEEPSEEK_API_KEY` |
